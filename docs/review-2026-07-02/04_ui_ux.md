## 全体所見

**設計の方向性は正しく、実装品質も研究プロトタイプとして水準以上。** frontend_renovation_plan.md のF1〜F4（JSON API → SSE差分配信 → 実行中モード切替 → 単一ファイルSPA）は計画どおり実装されており、旧「2秒ごと全リロード」からの脱却、ビルド不要・依存ゼロのバニラJS SPA、`ThreadingHTTPServer` によるSSEの非ブロッキング化（`_bootstrap.py:534-538`）など、判断は一貫して堅実。手動ファシリテーター呼び出しも manual_facilitator_call_plan.md の設計（Controller経路への統合、進行状況のSSE反映）に忠実で、UI上で「受付済み→待機中→発話済み/期限切れ」が追えるのは良い。

一方で、**「対面会議中にちらっと見る画面」としての情報設計は、操作卓（オペレータコンソール）と参加者向け表示が1画面に混在している**のが根本的な弱点。想定話者数・介入積極性・trigger_n・声紋名簿・モード切替といった「実験者/ホストが触るもの」と、議事録・発言量・介入通知といった「会議中に全員が見たいもの」が同じ密度で並び、会議中に一瞥して得られる情報（いま何が起きたか、AIが誰に何を言ったか）がむしろ埋もれている。presentation_policy.md が掲げる「個人宛の1行グランス通知」は現UIでは実現されておらず、介入理由はサイドバーの0.78remの小パネルに沈んでいる。

**信頼性の可視化が最大の穴。** STT切断・再接続はターミナルにしか出ず（`_bootstrap.py:741-759`）、ブラウザ側もSSE切断時に何も表示しない（`_webapp.py:728` の空 `onerror`）。会議中に文字起こしが黙って止まっても画面は「ライブ」のまま緑ドットが灯り続ける。議事録の欠落とAI介入の停止に誰も気づけない、というのは「会議に導入するツール」として最も避けるべき故障モード。

コード品質面では、755行のPython文字列にHTML/CSS/JSを埋め込む構成（`_webapp.py`、`replay.py` も同様）が限界に来ている。lint・型・テスト・シンタックスハイライトが一切効かず、`esc()` 手書きのテンプレートリテラル連結はXSS面でも監査しづらい。また毎秒フルスナップショットをSSEで送り、議事録DOMを `innerHTML` で全再構築する方式は、1〜2時間の実会議でペイロードと描画コストが線形増大し、テキスト選択が毎秒壊れる実害がある。

Streamlitビューア（評価用）は1325行の単一モジュールで、実行中はスクリプト全体がサブプロセスのstdout読みでブロックし、キャンセル手段がなく、リロードで子プロセスが孤児化する。ただしこれは研究者本人向けの評価UIであり、会議UXへの影響はない。viz/render.py は「デバッグ用ビューア」とdocstringで明示されており、位置づけとして適切。

## 指摘一覧

### Critical

#### C-1. 接続断・STT切断がブラウザUIに一切表示されない
- **file:line**: `src/das/asr/live/_webapp.py:728`（`src.onerror = () => { /* EventSourceが自動再接続する */ }`）、`src/das/asr/live/_bootstrap.py:741-759`（STT再接続は `print` のみ）、`src/das/asr/live/_session_state.py:473-512`（`api_snapshot` に接続健全性フィールドなし）
- **問題**: (1) サーバープロセスが落ちる/ネットワークが切れると、EventSource は裏で再接続を試み続けるが画面は最後の状態のまま「ライブ」表示。(2) STTのWebSocketが切れて再接続中でも、その事実は `api_snapshot` に含まれず、UIは文字起こしが止まった理由を示せない。
- **なぜ問題か**: 対面会議では全員が議論に集中しており、画面が「静かに古くなっている」ことに気づけない。議事録の欠落・介入の停止という最悪の故障が無音で起きる。会議支援ツールの信頼の根幹に関わる。
- **改善案**: ① `api_snapshot` に `stt_connected` / `last_audio_ms`（最終音声受信時刻）を追加し、UIで「⚠ 音声認識が切断中（再接続しています）」バナーを表示。② `onerror` で「サーバーとの接続が切れました」を status 表示に反映。③ 最後のSSE受信から N 秒経過したらステール警告を出す（クライアント側タイマーで実装可能、サーバー変更不要）。

### High

#### H-1. 毎秒フルスナップショットSSE配信 + 議事録DOMの全再構築
- **file:line**: `src/das/asr/live/_ui.py:64-76`（rev変化ごとに `api_snapshot()` 全体をシリアライズして送信）、`src/das/asr/live/_session_state.py:409-431`（`records` 全件を毎回変換）、`src/das/asr/live/_webapp.py:306-334`（`renderTranscript` が `box.innerHTML = parts.join("")` で全置換）
- **問題**: 会議が長くなるほど (a) JSONペイロード、(b) サーバー側のシリアライズコスト、(c) クライアント側のDOM全再構築コストが発話数に比例して増える。partial（認識途中）は発話中ほぼ毎秒変化するので、実質毎秒フル再送・フル再描画になる。
- **なぜ問題か**: 1〜2時間・数百発話の実会議で毎秒数百KBのJSON＋数百ノードのDOM再構築はジャンクの原因。さらに `innerHTML` 全置換のため、**議事録のテキストを選択・コピーしようとすると毎秒選択が解除される**。会議中に「さっきの発言をコピーしてチャットに貼る」という自然な操作ができない。
- **改善案**: `records` を追記イベントとして差分配信する（`rev` ベースで「rev N 以降の records」だけ送る）か、少なくとも transcript の描画を「既存ノードは触らず末尾に追記」方式に変える。partial は専用の1要素だけ更新。

#### H-2. AI介入がUI上で目立たず、「誰宛か」が一目で分からない
- **file:line**: `src/das/asr/live/_webapp.py:84-86, 313-319`（ファシリテーター発話は transcript 内の水色行のみ）、`_webapp.py:267-269, 397-415`（介入理由はサイドバー最下部の `.78rem` パネル、初期状態 hidden）
- **問題**: presentation_policy.md は「議論中の提示は個人宛の1行グランス通知」「全員向けは区切りで一文」と定めているが、実UIでは介入がスクロールする議事録の1行と、画面右下の小さな「介入理由」パネルにしか現れない。invite（発言の少ない人への声かけ）で対象者名が視覚的に強調されることもない。
- **なぜ問題か**: 音声介入を聞き逃した参加者が画面を見ても「いま何が起きたか」を1秒で把握できない。「ちらっと見る」ユースケースで一番見たい情報（最新の介入・宛先・理由）の視覚的優先度が最下位になっている。設計ポリシーと実装の乖離。
- **改善案**: 最新介入を画面上部に大きめの一時バナー（トースト）で表示する: 「🔵 AI → **田中さん**: 発言を促しました（理由: 発話量の偏り）」。30〜60秒で自動フェード。議事録内の該当行へのジャンプリンクを付ける。

#### H-3. 進行中のAI発話を止める手段がUIにない
- **file:line**: `src/das/asr/live/_webapp.py:171-177, 232-257`（ヘッダとパネルのボタン群に発話キャンセルなし。介入トグルは設定であり進行中の音声を止めない）
- **問題**: AIがタイミング悪く話し始めたとき、参加者ができるのは「被せて話す」か「介入オフに切り替える（次回以降にしか効かない）」だけ。
- **なぜ問題か**: レビュー観点の「介入を無視しやすいか」の核心。人間のファシリテーターなら空気を読んで引っ込むが、AIの発話は途中で止められない。1回の「うるさい」体験がツール全体の受容性を損なう。バックエンドには割り込み処理（partner interrupt / retry）が存在するのに、ユーザー起点の停止だけがない。
- **改善案**: 「🔇 いまの発話を止める」ボタンを常時表示（`response.cancel` + 音声出力の即時停止 + interventions.jsonl に `user_cancelled` を記録）。ついでに「30分介入を止める」スヌーズも一考。研究的にもキャンセル率は介入品質の良い指標になる。

#### H-4. Streamlit: 実行がブロッキングでキャンセル不能・子プロセス孤児化
- **file:line**: `src/das/ui/streamlit_app.py:965-1055`（`_run_eval_streaming` が `subprocess.Popen` の stdout をスクリプト内で同期読み。`finally` は `proc.wait()` のみで terminate 経路なし）、`streamlit_app.py:1207-1209`（実行ボタン押下と同じrun内で完了まで抜けない）
- **問題**: 実行中はStreamlitスクリプト全体が占有され、停止ボタンを置けない。ユーザーがブラウザをリロード/他操作するとスクリプト再実行が走り、読み手を失った `das eval` サブプロセス（実APIを呼び続ける）が孤児化する。
- **なぜ問題か**: LLM APIを叩く長時間ジョブが「見えないまま課金し続ける」事故につながる。評価UIとしても数十分のランを止められないのはつらい。
- **改善案**: proc を `st.session_state` に保持して「中止」ボタンで `terminate()`。もしくは実行はCLI起点に割り切り、Streamlitは「過去の結果を見る」専用に縮退させる（後者が最小工数）。

- **file:line**: `src/das/asr/live/_webapp.py:8-755`（`INDEX_HTML = """..."""`）、`src/das/asr/live/replay.py:44-231`（`REPLAY_INDEX_HTML`）

#### M-3. 声紋の事前登録: 20秒カウントダウンが見かけだけで、キャンセル不可・混入チェックなし
- **file:line**: `src/das/asr/live/_webapp.py:577-605`（クライアントで20秒 `setTimeout` を回してから `seconds=20` をPOST）、`src/das/asr/live/_ui.py:245-277`（サーバーは「直近20秒のPCMバッファ末尾」を無条件に切り出す）
- **問題**: (1) 録音はUIと無関係に常時走っており、カウントダウン中に他人が話したり雑談が入るとそのまま声紋に混入する（サーバー側の単独話者チェックは長さ2秒未満の拒否のみ）。(2) 開始したら20秒間キャンセルできない。(3) ページをリロードするとカウントダウンだけ消えて状態不明になる。
- **なぜ問題か**: セットアップフローの摩擦の核。N人会議で N×20秒+読み上げ台本の朗読を会議冒頭に強いる上、失敗（混入）が後の話者誤帰属として静かに現れるためデバッグ困難。
- **改善案**: ① キャンセルボタン追加。② サーバー側で該当区間のVAD/話者一貫性チェックを行い、疑わしければ再録音を促す。③ **「登録せず開始 → 自動クラスタリング → 気づいたときにサイドバーでリネーム」という既存の低摩擦動線を第一の動線としてUI上で明示**し、事前登録は「精度を上げたい場合のオプション」に格下げする。

#### M-4. モード切替がワンクリック即時・確認なし
- **file:line**: `src/das/asr/live/_webapp.py:293-304`（`div.onclick = () => setMode(m.id)`）、`696-710`
- **問題**: 画面上部の大きな3ボタンのどれかを誤クリックすると、即座にAIパートナーが接続/切断される（「AIと会話」はAIが音声で会議に入ってくる）。
- **なぜ問題か**: 会議中の最も破壊的な操作（AIの声が突然入る/介入が全停止する）が、最も押しやすい位置にノーガードで置かれている。
- **改善案**: 現在モード以外への切替は軽い確認（インラインの「切り替える?」ボタン）を挟む。少なくとも `transcribe`→`converse` のようにAIの音声が「増える」方向だけでも。

#### M-5. 介入パネルが研究パラメータと参加者操作の混在
- **file:line**: `src/das/asr/live/_webapp.py:232-257`（オン/積極性/「発話数」(trigger_n)/手動呼び出しが同一パネル）、`246-249`（「発話数」は何のことか説明なし）
- **問題**: 「発話数」ラベルは trigger_n（N発話ごとに介入を検討する間隔）だが、UI上に説明がなく、1〜50の数値入力だけがある。積極性との関係も不明。一方、同じパネルに参加者向けの「呼ぶ」がある。

#### M-6. 想定話者数セレクタが2箇所あり、送信元を `document.activeElement` で推定
- **file:line**: `src/das/asr/live/_webapp.py:617-633`（`setSpeakerCount` が activeElement で setup/side どちらの値を読むか決定）、`225-231`（変更が「新しい会議/再接続で確実に反映」という注記）

#### M-7. Streamlit: ライブ再描画がイベント毎に全ラン・全タイムラインを再構築
- **file:line**: `src/das/ui/streamlit_app.py:1039-1040`（イベント1件ごとに `_refresh_live_view`）、`1058-1090`（placeholder 内に全条件タブ＋全ランの全タイムラインを毎回描画）、`475-476`（切り詰め発話ごとに `st.expander` を生成）

## 対面会議介入UXとしての本質的な評価

### 1. 「画面を見る前提」自体の再検討

このシステムの介入チャネルは本質的に**音声（TTS）**であり、それは正しい。対面会議の参加者は互いの顔を見て話しており、画面を注視させる設計は会議そのものを壊す。presentation_policy.md 自身が「対面では人は喋っている → 議論中にグラフ図は出さない」と明言しているのは慧眼で、AF（議論グラフ）を内部表現に留めて「選ばれた一言」だけを出す方針は支持できる。

問題は、その前提に立つと**現在のブラウザUIが「誰のための画面か」が未定義**なこと。実態を分解すると:

- **ホスト/実験者の操作卓**: 起動・人数設定・声紋登録・モード切替・積極性・停止 — 会議前後と例外時のみ使う
- **参加者が「ちらっと見る」共有表示**: ライブ議事録・最新の介入と宛先・発言量バランス・議題 — 会議中に視界の端にある
- **事後レビュー**: replay UI・Streamlit — 会議後

現UIは1と2が同一ページに同じ密度で同居し、しかも `127.0.0.1` バインド（`_bootstrap.py:536`）なのでホストのPCでしか見られない。つまり「参加者がUIを見る」ためには、ホストPCの画面をプロジェクタに映すしかなく、そのとき積極性セレクタや声紋名簿まで全員に見える。**「/console（操作卓）」と「/board（共有ボード: 大文字の議題・経過時間・最新介入バナー・発言量バーだけ）」の2ビュー分離**が、最小工数で最も効く構造改善だと考える。将来、presentation_policy の「個人宛グランス通知」を本当にやるなら、LANバインド＋QRコードで各自のスマホに個人ビューを配る拡張が自然な延長線になる（現在の localhost 制約とは明確に矛盾するので、研究計画側と揃えるべき）。

### 2. 音声介入との使い分け

音声とUIの正しい分担は「**音声 = 介入の本体、画面 = 介入の記録・制御・拒否権**」だろう。現状は音声側は設計どおりだが、画面側の「記録」（H-2: 介入が目立たない）と「拒否権」（H-3: 止められない）が弱い。特に拒否権は重要で、人間のファシリテーターとの最大の差は「空気を読んで引っ込む」能力の欠如であり、それを補うのは参加者側の安価な停止手段（ワンタップのキャンセル/スヌーズ）しかない。これは研究上も「介入がキャンセルされた率」という直接的な受容性指標を生むので、実装する価値が高い。

また invite（発言の少ない人への声かけ）は名指しの音声介入であり、対象者にとって心理的負荷が最も高い介入。せめて画面上で「なぜ自分が指名されたか」（発話量バーと連動したハイライト）が見えると、納得感（RQ3の intervention_transparency）に直結する。現在は発言量パネルと介入理由パネルが独立していて、この因果が画面から読み取れない。

### 3. セットアップ摩擦

会議は「始めよう」と思った瞬間に始まる。人数選択→声紋の20秒×N人朗読というフローは、実際の会議では最初の1回で嫌われるリスクが高い。幸い本システムには「登録なしで開始→自動クラスタ→話者1/話者2を後からリネーム（声紋は次回に持ち越し）」という優れた低摩擦経路が既にあるので、**既定動線を「とにかく開始」にし、声紋事前登録は精度オプションに降格**させるのが正しいプロダクト判断。加えて2回目以降は voices.json で自動認識されるのだから、「前回のメンバーを認識済み: 田中・佐藤・鈴木」と開始画面に出すだけでセットアップ体験は大きく改善する。

### 4. 総括

バックエンドの介入品質制御（Controller・クールダウン・沈黙待ち・手動呼び出しのログ追跡）はよく設計されており、UIの弱点は主に「情報の優先順位」と「故障の可視化」に集中している。C-1（接続断の可視化）と H-3（発話キャンセル）は少ない工数で信頼性と受容性を大きく上げる。逆に大規模なUI刷新（React化など）は現段階では不要で、単一ファイルSPA方針のまま、ファイル分離（M-1）と2ビュー分離を段階的に進めるのが妥当。
