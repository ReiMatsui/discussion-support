# ADR-003: ノードは問いと案の2種。賛否は属性、理由は非表示

- 状態: 採用
- 日付: 2026-10-01
- 関連仕様: [02_data_model.md](../spec/02_data_model.md)

## 背景

議論グラフのノードを何にするかを決める必要があった。IBIS（問い・案・賛成・反対）や、既存の AF
（主張・前提・根拠と支持・攻撃）は、テキストでのやり取りや事後の分析では使われてきたが、
リアルタイムに音声から作って参加者に見せる場合に適しているかは分からなかった。

## 選択肢

| 案 | ノード | 問題 |
|---|---|---|
| A. IBIS の全種類（MeetMap） | 問い・案・賛成・反対 | 賛否の取り違えと重複が出る。ノード数が多い |
| B. 問いと案の2種類（EchoMind） | 問い・案 | 誰がどの立場かが見えない |
| C. 話題の区切り（TalkTraces） | 話題 | 何が決まったかを表せない |
| D. 主張と前提（現行 AF） | 主張・前提・根拠 | 関係の推定が最も難しく、ひと目では読めない |
| **E. 問いと案＋立場の属性** | 問い・案。賛否は話者の属性 | — |

## 決定

E を採用する。問いと案だけをノードにし、IBIS の賛成・反対はノードにせず「誰がどの案に賛成か・
懸念があるか」という話者の属性にする。理由（論拠の内容）は内部に保存し、画面には出さない
（理解に時間がかかるため。高田の判断）。

## 理由

リアルタイムのノードに求める条件と、それを満たすかで判断した。

| 条件 | 根拠 |
|---|---|
| 発話の時点で判別できる | 論拠の関係は後の発話を待たないと決まりにくい。対話の支持・攻撃関係の自動推定は最高でも F1 48（DialAM-2024）。問いや提案は「〜どうする？」「〜にしたら？」のように発話の時点で判別しやすい |
| 後から直さなくて済む | 表示済みの構造を組み替えない要件（R3）と両立する |
| 種類が少なく、ひと目で読める | EchoMind は予備実験で論拠ノードを「リアルタイムには不要」として削除した。MeetMap では賛否の取り違え、重複ノード、粒度への不満が報告された |
| まとめた単位にする | 実会議の発言単位の約4割は議論外（TAS、Verbree et al. 2006） |
| その場で役立つ | 会議記録への問い合わせの約6割が論点と結論（Pallotta et al. 2007） |

- IBIS はもともと会議の場で書記が描く手法（Conklin の Dialogue Mapping）だが、熟練した書記が前提で
  あり、自動化して全種類を描くと誤りが目立つ。
- 立場を「話者の属性」にすると、提案文同士の論理関係を推定するより問題が狭くなり、誤っても印が
  1つずれるだけで済む（精度が上がるかは仮説として実測で確かめる）。
- 本プロジェクトの話者同定を立場の表示に使えるため、研究の2本柱（話者同定と議論構造）がつながる。

## 影響

- 論拠の構造（どの理由がどの案を支えるか）は画面からは分からない。AI ファシリテーターは内部の
  理由を参照できる。
- 立場の判定の設計が必要になる（[ADR-009](ADR-009-stances.md)）。
