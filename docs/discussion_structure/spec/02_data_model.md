# 02. データモデル

関連する設計判断: [ADR-003](../decisions/ADR-003-node-types.md)、
[ADR-004](../decisions/ADR-004-answer-types.md)、[ADR-005](../decisions/ADR-005-agenda-and-tree.md)

## 1. ノード【合意】

**Issue（問い）**

| 属性 | 意味 |
|---|---|
| `id` | 会議内 ID |
| `label` | 表示用の短い問い（≤ 20 字、疑問形）。作成後は自動で変えない（格上げを除く） |
| `answer_type` | `yes_no`（是非型）/ `choice`（選択型）/ `open`（自由回答型）。§2 |
| `parent_id` | 親（根の議題、別の Issue、または Position） |
| `status` | 解決状態（§5） |
| `decided_answer` | 是非型の決定内容（`yes` / `no`） |
| `stances` | 是非型のときの話者の立場（§6） |
| `source_turns` | 導入・言及した発話の ID |

**Position（案）**

| 属性 | 意味 |
|---|---|
| `id` | 会議内 ID |
| `label` | 表示用の短い案（≤ 16 字）。作成後は自動で変えない |
| `parent_id` | 親の Issue（選択型・自由回答型のみ） |
| `status` | `proposed` / `adopted` / `rejected` |
| `stances` | この案への話者の立場（§6） |
| `reasons` | 理由の要約と根拠発話（**内部のみ。画面に出さない**） |
| `source_turns` | 根拠発話の ID |

## 2. 問いの答えの型【合意】

| 型 | 例 | 下に付くもの |
|---|---|---|
| 是非型 | 「紙ストローに切り替えるか？」 | 案ノードは作らない。問い自体に立場を付ける |
| 選択型 | 「紙とバイオプラのどちらにするか？」 | 選択肢の案ノード |
| 自由回答型 | 「費用をどう賄うか？」「なぜ売上が落ちたか？」 | 出てきた案ノード（理由・方法・数量の問いもここ） |

## 3. 構造（木）【合意】

- 画面に出す構造は**単一親の木**とする。親子関係は次の3種だけ。
  - Issue → 子 Issue（下位の問い）
  - Issue → Position（選択型・自由回答型のみ）
  - Position → Issue（案に対して生じた問い。例:「その案の費用は？」）
- 木に収まらない関係（ある問いが別の問いに依存する等）は内部関係として保存し、表示しない。
- 木の深さはデータ上は制限しない。段数は経路上の Issue の数で数える（表示は
  [09_display.md](09_display.md)）。
- 議題ごとに木を分ける（§4）。

## 4. 根（議題）と会議前の設定

**議題**【合意】

- 議題は「その会議で何を決める・話し合うか」を表す、木の根の Issue である。
- **会議の前に人が設定する**。会議前の設定項目は「議題」と「終了時刻（または時間）」の2つ。
  既存のライブ基盤には UI の議題編集（`set_agenda`）と起動時の `--topic` がある。
- 設定がない場合は、既存の推定処理（`_AGENDA_PROMPT`）で冒頭の発話から仮の議題を立てる。
  推定できるまでは「（議題未設定）」を根にする。
- 議題は短い句のまま表示し、判定モデルと LLM には問いの形（「学食の環境対策として何をするか？」）
  でも渡す。
- 議題の小項目を事前にノードとして置くことはしない。根の下はすべて議論から作る。
- 議題は脱線検知（[08_drift.md](08_drift.md)）の判定の軸と同じものを使う。

**議題の変更**【未確認の提案: 2つの操作を UI で分けること】

| 操作 | 例 | 木の扱い |
|---|---|---|
| 議題の修正 | 推定した仮の議題を正しい文言に直す | 根のラベルだけを変える |
| 次の議題へ移る【合意】 | 「ストローの件」から「容器の件」へ | 新しい木を作る。前の木は保存して画面から外す |

- 次の議題へ移るとき、前の議題のまとめを行う（[07_resolution.md](07_resolution.md)）。
- 前の議題の木は記録として残し、過去の議題の一覧から選んで再表示できる。
- 話者の登録や名前は会議単位で引き継ぐ。会議全体を区切る既存の「新しい会議」とは別の操作。
- 脱線検知の軸も新しい議題に切り替える。
- UI を操作しないまま話が次の議題に移った場合は脱線として検知されるため、AI が
  「議題を切り替えますか？」と尋ねる（[10_ai_voice.md](10_ai_voice.md)）。

## 5. 問いの解決状態【合意】

| 状態 | 内部の対応（QUD 設計） | 付く条件（[07_resolution.md](07_resolution.md)） |
|---|---|---|
| 未解決 | open / partially_resolved | 既定 |
| 決定 | resolved | 明示的な決定と同意、またはまとめの段階での確認 |
| 保留 | suspended | 明示的な保留の発話、またはまとめの段階で「持ち帰り」 |
| 取り下げ | abandoned | 明示的な取り下げの発話 |

焦点（いま議論中か）は解決状態とは別に持つ。決まった問いを再び議論することもあるため、
画面では両方を同時に表せるようにする。

## 6. 話者の立場【合意】

- 是非型の Issue と各 Position に、話者ごとの立場を1つ持たせる。値は**賛成**と**懸念**。
  中立・不明は記録しても表示しない。
- **懸念**は反対に限らず、**まだ解消されていない懸念がある状態**を表す。条件付きの賛成
  （「いいと思う、でも高くない？」）も懸念に含める。
- 各立場には安定話者 ID、話者帰属の確信度、立場の確率、根拠発話を保存する。
- 懸念の中身（「費用が高い」）は理由として内部に保存し、画面には出さない。
- 立場の更新は属性の変更であり、構造の変更ではない。
- 判定と更新の規則は [06_stances.md](06_stances.md)。

## 7. 記録

- QUD 試作と同じく、追記型のイベントログと現在状態のスナップショットを保存する。
- 画面の変更はすべて `display_commit` として記録し、安定性の指標をログから計算できるように
  する（[11_evaluation.md](11_evaluation.md)）。
- 立場・状態の変更はすべて遷移イベントとして記録する。
- 自動では適用しない構造の変更（統合・付け替えなど）は「構造提案」として記録する。
