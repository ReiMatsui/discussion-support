# 12. 実装方針

関連する設計判断: [ADR-002](../decisions/ADR-002-branch-and-base.md)

## 1. 土台とブランチ【合意】

- 作業ブランチは `takada/discussion-structure`（`main` から作成）。
- 実装の土台は `main`。`main` には GPT-Live の試験導入（`agents/_live.py`）がある。
- `origin/feat/live-native`（Rei）の変更（話す層の一本化、脱線の状態機械）は、Rei のマージ後に
  取り込むか、必要な部分を本ブランチ側で移植する。**Rei のブランチは変更しない**。
- 実装は Codex が担当し、本ディレクトリを受け渡しの正本とする。push と PR は高田の指示が
  あるまで行わない。

## 2. QUD 試作との違いと移植の候補

| 観点 | QUD 試作 | 本設計 |
|---|---|---|
| 目的 | 観測・保存のみ | 参加者と AI への提示 |
| ノード | 問いのみ | 問い＋案（立場つき） |
| 根 | なし | 議題 |
| 判定 | 数発話ずつまとめて LLM | 発話ごとの判定モデル＋規則 |
| 構造の更新 | LLM 出力を検証して自由に適用 | 許可した変更のみ |
| 焦点 | active を複数持てる | 常に1つ、平滑化つき |
| LLM 入力 | 毎回全状態 | 焦点の周辺だけ |

QUD 試作（`takada/qud-inquiry`、`4e1df14`）は参照用として残し、`main` へは取り込まない。
次の部分は移植の候補とする。

- 入力の振り分け（`src/das/QUD_inquiry/input_contract.py`）
- 安定話者 ID と遡及訂正（`speaker_identity.py`、`runtime.py` の訂正処理）
- 会議境界のリセット、再試行と稼働状態
- 遅延の計測、イベントログとスナップショットの保存形式
- 解決根拠の要件と、検証の境界の考え方

## 3. 段階

1. **設計確定**: 未決事項（[open_issues.md](open_issues.md)）のうち、実装に先立つものを決める。
   判定モデルの入出力と状態遷移を定義する。
2. **オフライン試作**: 保存済みの議事録（turns.jsonl）を再生して木を作る。焦点・ノード作成・
   立場・決定の振る舞いと、ログからの指標を確認する。判定モデルの候補もここで比較する。
3. **画面**: ライブ UI に静かな画面を追加する。
4. **AI の声**: 介入の種類の追加、まとめの段階、訂正、問い合わせへの答え。
5. **評価**: 人手注釈による技術評価、視聴実験、ライブ試行。
