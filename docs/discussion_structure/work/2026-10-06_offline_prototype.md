# 作業依頼: オフライン試作（議事録の再生から木を作る）

- 状態: approved（2026-10-06、高田）
- 依頼元: Claude Code（設計）
- 担当: Codex（実装）
- 正本: `docs/discussion_structure/`（コミット `dafd69e` 以降）。仕様と食い違う場合は仕様を優先し、
  食い違いは報告に書く。仕様書（`spec/`・`decisions/`）は編集しない。

## 1. 目的

保存済みの議事録（`turns.jsonl`）を発話ごとに再生し、仕様どおりに議論の木（問い・案・立場・焦点・
解決状態）を作る処理を、ライブ基盤から切り離して実装する。規則が仕様どおりに動くことをテストで
確かめ、判定モデル（速い層）を差し替えて比較できる土台を作る。

対応する段階: [12_implementation.md](../spec/12_implementation.md) §3 の「2. オフライン試作」。

## 2. 範囲

**含める**

| 仕様 | 内容 |

| [03_utterance_judgement.md](../spec/03_utterance_judgement.md) | 速い層の判定インターフェース、遅い層（ラベル生成）、入力の範囲 |
| [04_focus.md](../spec/04_focus.md) | 焦点の平滑化と切替 |
| [05_nodes.md](../spec/05_nodes.md) | 作成のきっかけ、応答待ち、同一性、配置、格上げの手順、ラベルの検査 |
| [06_stances.md](../spec/06_stances.md) | 立場の判定・閾値・更新（乗り換えを含む） |

| [11_evaluation.md](../spec/11_evaluation.md) §2 | ログから計算する指標 |

**含めない**

- 画面の描画（UI）、AI の声（GPT-Live・Controller）、まとめの段階の対話（決定候補の一覧を出す
  ところまでは行う）
- 脱線の状態機械（`DriftRun`）の移植。速い層の `on / aside / off` の判定は記録し、`off` の発話から
  ノードを作らない規則だけを実装する
- ライブ基盤への組み込み。`src/das/asr/live/` を含む既存モジュールは変更しない
- QUD 試作（`takada/qud-inquiry`）からの移植（今回は参照のみ）

## 3. 入力

- `turns.jsonl`: 1 行 1 発話。`turn_id`、`speaker`、`text`、`ms`、`end_ms`。あれば `speaker_confidence`、
  `unsure`（未確定話者）、`speaker_uid` も読む。現在の `main` が書き出す形式は
  `src/das/asr/live/_session_state.py` の turns の書き出しを参照。
- 議題: コマンドの引数で与える（例: `--agenda "学食の環境対策"`）。
- 実データはほとんどない（`transcripts/2026-06-25_1654.turns.jsonl` の 16 発話のみ）。そのため §5 の
  シナリオを作る。

## 4. 作るもの

### 4.1 モジュール

`src/das/discussion_structure/` に新設する。構成は次を目安とし、必要なら変えてよい（報告に書く）。

| ファイル | 役割 |
|---|---|
| `models.py` | Issue、Position、Stance、木、イベント、構造提案（pydantic、frozen を基本） |
| `config.py` + `configs/discussion_structure.toml` | 閾値・時間（[open_issues.md](../spec/open_issues.md) §4 の暫定値）を1か所で管理。秘密情報は置かない |
| `views.py` | 判定モデル・LLM に渡す入力（議題から焦点までの経路、焦点の部分木、他の未解決の問い、直近の発話） |
| `judgement.py` | 速い層のインターフェース（選択肢と確率を返す）と実装（下記） |
| `focus.py` | 焦点の信念の更新と切替（事後確率 0.7、2 発話かつ 10 秒） |
| `nodes.py` | 作成規則、応答待ちの候補（60 秒）、同一性、配置、格上げの手順 |
| `labels.py` | 遅い層: ラベルと答えの型の生成、規則による検査（文字数・疑問形・個人名なし）、1 回の作り直し |
| `stances.py` | 立場の閾値（0.8）、更新、選択型の乗り換え、自由回答型の追加、懸念の扱い |
| `resolution.py` | 自動の決定（同意 1 件以上、懸念なし、10 秒異議なし）、保留、取り下げ、決定候補、再開 |
| `display.py` | 表示状態（はっきりしたものだけ）、反映間隔、段数、ノード数上限と折りたたみ、`display_commit` |
| `tracker.py` | 発話ごとに上記を順に呼ぶ本体。時刻は議事録の `ms` / `end_ms` を使う（壁時計を使わない） |
| `replay.py` | コマンド（§4.3） |
| `metrics.py` | ログからの指標と、シナリオの期待結果との照合 |

### 4.2 速い層の実装

判定は「選択肢と確率を返す」共通のインターフェースにし、次を実装する。

| 実装 | 内容 |
|---|---|
| `scripted` | シナリオに書いた判定をそのまま返す。規則のテスト用（API を呼ばない） |
| `openai_logprobs` | OpenAI の LLM で、各判定項目を1トークンの選択肢として出させ、対数確率から確率を得る。既存の `das.llm.OpenAIClient` か `openai` SDK を使う。モデルは設定で指定 |
| `jev` | TypeSafe AI の Jev。環境変数 `TYPESAFE_API_KEY` がなければ明確なエラーで止まる。API の形は公式文書（https://docs.typesafe.ai）に従う。キーがない環境では単体テストだけ（通信部分は差し替えて試す） |

Decisions API（OpenAI）は仕様が未公開のため、今回は作らない。

判定項目は [03_utterance_judgement.md](../spec/03_utterance_judgement.md) §2 の表のとおり（「新しい案が
代わりか追加か」を含む）。1 発話につき判定にかかった時間を記録する。

### 4.3 コマンド

```bash
uv run python -m das.discussion_structure.replay <turns.jsonl> \
  --agenda "学食の環境対策" --backend scripted|openai_logprobs|jev \
  [--scenario <シナリオ.json>] [--out <出力先>]
```

出力先（既定は `data/discussion_structure/<入力名>/`。`data/` は Git 管理外）:

| ファイル | 内容 |
|---|---|
| `events.jsonl` | 判定結果、構造の変更、立場・状態の遷移、構造提案、`display_commit` |
| `snapshot.json` | 最終状態（内部状態と表示状態の両方） |
| `timeline.txt` | `display_commit` ごとの表示状態を、字下げの一覧で書いた人が読む記録 |
| `metrics.json` | [11_evaluation.md](../spec/11_evaluation.md) §2 の指標、判定の遅延（p50 / p90）、API 費用 |
| `scenario_check.json` | シナリオがある場合、期待結果との一致・不一致の一覧 |

## 5. シナリオ（テスト用の議事録）

日本語の議論の短い台本を作り、`tests/fixtures/discussion_structure/` に置く。各シナリオは、
発話（話者・本文・時刻）、`scripted` 用の判定、期待する結果（最終の木と、途中の要所の状態）を持つ。
少なくとも次の場面を含める（1 シナリオに複数含めてよい）。

| 場面 | 確かめること | 仕様 |
|---|---|---|
| 明示的な問い | すぐ Issue ができる | 05 §2 |
| 単独の提案に応答がある／ない | 応答があれば是非型ができ、60 秒応答がなければ候補が消える | 05 §2 |
| 代わりの案による格上げ | 仕様の例どおりに型・ラベル・案・立場が変わり、子は動かない | 05 §5 |
| 追加の案 | 格上げせず、別の是非型になる | 05 §2 |
| 懸念と、懸念の中身が話題になる | 子の Issue ができる。理由に使っただけでは作らない | 05 §2、06 §5 |
| 相槌・「そうですね、ただ…」・沈黙 | 相槌は印にならない、前置き＋逆接は懸念、沈黙は何もしない | 06 §2 |
| 選択型の乗り換え／自由回答型の追加 | 選択型は前の賛成が外れ、自由回答型は残る | 06 §4 |
| 焦点の深掘り・戻る・横移動・一瞬の寄り道 | 閾値と継続時間を満たしたときだけ切り替わり、寄り道ではちらつかない | 04 |
| 明示的な決定／懸念が残る決定／異議 | 条件を満たすときだけ決定。懸念が残れば決定候補になる | 07 §1・§2 |
| 決定の再開と、決定済みの問いへの代わりの案 | 応答があれば未解決に戻り、その後に格上げ | 07 §4、05 §5 |
| 脱線（`off`） | ノードを作らない | 08 |
| 未確定話者 | 印は「?」になり、名前を出さない | 06 §3 |

## 6. 完了条件

1. `scripted` で全シナリオを再生し、期待結果と完全に一致する（`scenario_check.json` で不一致 0）。
2. 規則ごとの単体テストがある（上の表の各場面）。`uv run pytest -q` が通る。既存のテストを壊さない。
3. `uv run ruff check .` で新しい警告を増やさない（既存の警告と区別して報告する）。
4. 既存の `transcripts/2026-06-25_1654.turns.jsonl` を `openai_logprobs` で再生して、落ちずに出力が
   揃う。
5. `openai_logprobs` で全シナリオを再生し、判定項目ごとの一致率、判定の遅延（p50 / p90）、確率の
   較正の目安（確率の区間ごとの正解率）、API 費用を報告する。**API 費用は合計 2 ドルまで**とし、
   超えそうなら止めて報告する。
6. `jev` は、キーがない環境で明確なエラーになり、通信部分を差し替えた単体テストが通る。

## 7. 進め方の約束

- `takada/discussion-structure` の最新コミットから `codex/discussion-structure-offline` ブランチを作り、
  そこで作業する。段階ごとにコミットする（1 コミット 1 目的）。
- push と PR はしない。共同研究者のブランチ（`origin/feat/live-native` など）は変更しない。
- `.env`、API キー、音声、実データの出力をコミットしない。
- 仕様が曖昧なところは、仕様と矛盾しない最も単純な解釈で実装し、報告に一覧で書く。仕様書は
  編集しない。
