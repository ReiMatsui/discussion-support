# GPT-Live への全面移行と、それに最適化したリファクタリングの計画（2026-09-13）

> 状態: 計画。着手前に §9 の判断をもらう。作業はブランチ `feat/live-native` で行い、
> 各作業単位（WP）ごとにコミットし、検証の関門を通ってから次へ進む。
> 根拠: `docs/research/gpt_live_api_2026-09.md`（API の事実と実測）、
> 2026-09-12〜13 の通し・実マイク試行。

## 1. 目的と、やらないこと

目的は2つ。話す層を GPT-Live-1 に一本化し、Realtime API 前提で積み上げてきた
割り込み・エコー・再送まわりの自前処理を、GPT-Live の全二重に任せられる分だけ
取り除くこと。そのうえで「いつ・誰に・何を」を決める層（Controller）と話者同定の
層は一切変えず、実験の統制を保つこと。

やらないこと。話者同定（Soniox＋pyannote＋声紋）と Controller の判断規則には
触れない。介入の種類や採択の閾値も変えない。GPT-Live の委任（responses）で
背後の LLM を回す構成にはしない（介入の内容は Controller が決める設計を守る）。

## 3. GPT-Live に合わせた設計の要点

### 3.1 責務の切り分け（変えない）

Controller が「いつ・誰に・何を」を決めて `trigger(...)` を呼ぶ。LiveAgent は
それを GPT-Live への指示に変換して話させ、話した文字を議事録に返す。
GPT-Live が自分で判断するのは、割り込まれたときの止まり方と再開、それと
参加者から直接呼びかけられたときの短い応答だけ。

### 3.2 セッションの扱い

- 会議1つにつき GPT-Live セッション1つ。開始時に指示文・声・音声形式・
  委任（client）を固定する。指示文は会議中に変えない。
- 室内の音声は常に送る（`listen="always"` を既定にし、`idle`/`never` は消す）。
  送らない間も無音で時計を進める仕組みは、マイクが止まったときの保険として残す。
- モード切替は「セッションを閉じて別の指示文で開き直す」。議事録のみ＝
  セッションなし、人間に介入＝進行役の指示文、AIと会話＝会話相手の指示文。
  声の変更も同じ経路（開き直し）。
- 委任要求（delegation.created）には「追加処理は不要」と返す。将来、背後の
  推論を GPT-Live 側に任せる案はこの層の外で検討する。

### 3.3 割り込み・再開・エコー

- 人の発話による停止と再開は GPT-Live に任せる。こちらは検出しない。
  こちらが持つのは、再生の停止（「新しい会議」「終了」「介入オフ」のとき）だけ。
- 「中断された介入を後で再送する」仕組みは廃止。再開はモデルが行う（実測で
  「はい、続けます」と自然に再開した）。再開しなかった場合は Controller が
  次の機会に新しい介入として判断する（既存の規則で足りる）。
- 生成先行（hold/release）は廃止。GPT-Live は音声を実時間で流すので、
  溜めておいて後で一斉再生するとモデルの時間とずれる。代わりに Controller は
  「フロアが空いた」と判断した時点で指示を送る（指示から声まで 0.5〜4.6 秒）。
  この遅延は測定して記録し、必要なら指示文の短縮で詰める（§7）。
- Soniox 側のエコー（AI の声が文字になる）は従来どおり AI 声紋フィルタと
  テキスト類似の安全網で除く。GPT-Live 側のエコー（自分の声を聞く）は
  実測で問題が出なかったので対策しない。出たときの逃げ道として
  `--live-listen idle` 相当の運用は残さない（複雑化の元）。代わりに
  エコー除去つきスピーカーフォンの利用を手順書に書く。

### 3.4 発話の境界と議事録

- 出力音声は無音を含む連続ストリーム。声の区間を音量で切り、無音が
  1.2 秒続いたら1発話とする（実測で「承知。…えっと」の間を割らない長さ）。
- 文字は `output_transcript.delta` を溜め、発話の終端で確定して議事録に入れる。
  ストリームが3秒止まったときの保険も残す。
- 指示を送って 15 秒話し始めなければ諦めて次に備える。

### 3.5 記録（実験で使う値をここで確定する）

介入ログに次を残す。指示から最初の声までの遅延、発話の長さ、人の発話が
重なった時刻とモデルが黙るまでの時間、モデルが自分で再開したか、
呼びかけ以外でモデルが口を挟んだ回数。§7 の比較と論文の記述に使う。

## 5. 進め方の規律

- 1 WP = 1 コミット（大きければ数コミット）。コミットメッセージは WP 番号から始める。
- 既存のテストを消すのは、置き換えるテストを同じコミットで入れるときだけ。
- Controller・話者同定・採点（eval/）のファイルは触らない。触る必要が出たら
  止めて相談する。
- 各 WP の後に `uv run pytest -q` と `ruff check` を通す。通らない状態で次に進まない。
- Mac が正本。クラウド側で書いたファイルは WP ごとにまとめて Mac に入れ、
  Mac で `git add` と `git commit` をする（コミット文はこちらで用意する）。
- 動作確認は Mac でしかできない（API キー・マイク）。各 WP の関門で
  何を実行してどの行を見るかを、その都度1行で指定する。

## 6. 危険と備え

| 危険 | 備え |
|---|---|
| GPT-Live が呼びかけ以外で口を挟む（統制の崩れ） | 指示文で禁じる（実測では 3 回中 1 回、旧版で発生）。WP9 で回数を数え、1回でも出るなら指示文を締める。それでも残るなら「呼びかけ以外で話したら Controller が介入とみなさず議事録にも入れない」を最後の手段として用意 |
| 指示から声までの遅延が大きい回がある（4.6 秒） | 遅延を記録し、指示文と文脈を短くして詰める。Controller の「間」の判断は遅延込みで見直さない（規則を変えない） |
| API の仕様変更（公開 3 日目） | イベント名と URL を定数に集約し、`live_smoke.py` を回帰確認に使う |
| 費用（常時接続 $0.05/分） | 1 時間 3 ドル。実験全体でも数十ドル。問題なし |
| Realtime 版を消した後に戻せない | `midterm-2026-09` タグと `main` に残る。戻すのは `git checkout` で済む |
| 「AIと会話」モードの扱い | §9 で先に決める。移すなら WP7、消すなら UI からも外す |
| 自分の声の回り込みで GPT-Live が混乱する（今回は出なかった） | 出た会場では外付けのスピーカーフォン。手順書に書く |

## 7. 測って残すもの（Realtime 版との比較）

`midterm-2026-09` 時点の Realtime 版で同じ試行を1回だけ行い、次を並べる。

- 指示から最初の声までの遅延（中央値・最大）
- 人が被せてからモデルの声が止まるまでの時間
- 呼びかけ以外の発話の回数
- 議事録に入った AI 発話が実際の発話と一致するか（割れ・混ざりの有無）
- 削除した行数（`_realtime.py`・割り込み・生成先行・再送）

これは論文の「実装」章に、話す層の置き換えで何が不要になったかとして書ける。

## 8. 論文への影響

主張は変わらない。「いつ・誰に・何を」を決める層と話す層を分けているので、
話す層が Realtime から全二重モデルに変わっても Controller と話者同定は
そのまま、という事実がむしろ設計の主張を強める。考察には「全二重モデルは
割り込みの扱いを引き受けるが、誰が言ったかは依然として返さない」と書く。

## 9. 先に決めてほしいこと

1. 「AIと会話」（partner）モードを Live に移すか、修論の範囲外として落とすか。
   実験では使わないので、落とすのが簡素化の趣旨に合う。
2. 参加者から直接呼びかけられたときに GPT-Live が短く答えることを、実験でも
   許すか。許すなら「介入」とは別の種類として記録する。許さないなら指示文で
   禁じ、それでも出たときの扱いを決める（§6）。
3. Realtime 版のコードを WP8 で削除してよいか（タグと履歴には残る）。
4. 声（marin 以外を試すか）。

決まったら WP0 から始める。
