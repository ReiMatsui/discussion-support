## 1. 問題（実測で確定済み）

ハイブリッド構成では、同じ人間が2つの帳簿に別名義で載る:

- **クラスタ帳簿**: diarizationクラスタ → `@diar:N`（`diarization_speaker_keys`）
- **声紋帳簿**: STTラベルの声紋蓄積が鋳造する `人物N`（`VoiceProfiles._commit_profile`）

実会話ログでの実証（声紋を再計算して突き合わせた結果）:

| セッション | 事実 |

| 2026-07-25_1723 (2人) | 参加者A(@diar:1) と 参加者B(人物1) が **類似0.613=同一人物**。1人が2席を独占 → 2人目は席なしで大半未確定、終盤に人物2（=2人目、別人）が「参加者C」として出現 |

- 別人ペアの類似は 0.03〜0.31、同一人物ペアは 0.61〜0.70 と**綺麗に分離**。
- 既存の統合機構（クラスタ確定, `ClusterVoiceNamer.observe` → 確定バー
  `PYANNOTE_CLUSTER_CONFIRM_MIN_SIM=0.65`）は 1723 で類似0.613を**0.04差で

  「参加者Cの出現」は止めたが、席の二重取りそのものは残っている。

## 2. 承認済みの方針

**根治 = 人物の鋳造窓口をクラスタ経由に一本化する**。設計候補は2つあり、
Phase 0 の数字で決める:

- **案A（鋳造一本化）**: ハイブリッド時、STTラベル側の鋳造
  （`_commit_profile` の新規人物作成）を停止し（照合・分類は継続）、
  クラスタ側に鋳造を移す（クラスタに十分なクリーン音声が溜まり、既存の
  誰とも dedupe 以上で一致しなければ、クラスタ代表声紋で人物Nを鋳造して
  即 confirm/rekey）。1人=1クラスタ=1戸籍=1席。
- **案B（鋳造時リンク）**: ラベル側の鋳造は残すが、鋳造の瞬間に
  「新人物のプロファイル vs 席持ちクラスタの蓄積声紋」を**対称比較**し、
  閾値（実測分離から0.45前後が候補）以上なら新席を作らずそのクラスタ
  IDに統合する。変更が局所的で、確定バー0.65の一方向照合より情報量の
  多い比較になる。

### 7.1 二重帳簿は常態だった

記録16本の鋳造（自動登録）36件のうち、**28件（78%）が「既に席を持つ人物の
二重登録」**。§1 で実証した 1723/1641 だけの事故ではない。

### 7.2 リンク判定（案Bの核）は成立する

鋳造の瞬間に「鋳造したてのプロファイル vs 席持ちクラスタの蓄積声紋」を
**対称比較**したときの精度（argmax・各鋳造1回）:

| 閾値 | リンク成立 | 正 | 誤 | 取り逃し |
|---|---|---|---|---|
| 0.50 | 28 | 25 | 2 | 0 |
| 0.55 | 22 | 21 | 0 | 4 |

同一人物の対称類似 0.50-0.88 / 別人 0.07-0.52 で分離する。**確定バー0.65 が
見送っていた 1723 の片方向0.63 は、対称比較なら 0.705**——両側とも蓄積音声から
声紋を作るため。バーを下げるのではなく比較の仕方を変えるのが正しい、という
根拠になった（0.65 は据え置き）。

実装で使える演算（人物側＝発話ごと声紋の平均 or 蓄積音声の連結）への
置き換えでも th=0.50 で 正24/誤1 とほぼ同等＝**閾値は移植できる**。

### 7.3 案B「遅延」は棄却（重要）

「鋳造時1回」ではなく「クラスタ蓄積が伸びるたびに再判定」する案を、各クラスタの
累積が 5/10/20/40/80/160 秒を超える時点でその瞬間のバッファを比較する時系列
シミュレーションで検証した結果、**分離が消える**:

- 別人ペアの判定点 sim: 0.693 / 0.677 / 0.626 / 0.584 / 0.568 / 0.525
- 同一ペアの判定点 sim: 0.534 / 0.605 / 0.745 / 0.761 / 0.783 …
- argmax＋margin 0.10＋席音声下限10秒まで足しても 正3-5/誤1-3（誤り率20-40%）

機序: (a) 短い断片クラスタは誰にでも似る（1635 @diar:3=6.5秒は人物1に0.693・
人物3に0.534〈真〉・人物2に0.502 と3人全員に中程度似るため margin も効かない）、
(b) バッファの直近20秒が別人の声になることがある（1723 @diar:1 は全量なら0.73、
直近20秒だと0.05）。

これは §15.12 で「クラスタ埋め込み同士に分離可能な閾値は存在しない」と実測し
§18.9 で機構ごと削除したクラスタ間名寄せと**同じ失敗モード**。繰り返し判定は
「最悪の読みがいつか必ず当たる」露出を作る。一発勝負が成立するのは、鋳造時の
プロファイルが純度検査を通った登録材料から作りたてで、比較が1回きりだから。

### 7.4 案A（鋳造一本化）は採らない

GT11本平均で実質 29.1%（悲観）/ 35.4%（楽観）と、案B（53.1%）より19pt低い。
誤帰属は最小（13.2-15.2%）だが代償が大きすぎる。

ただしこの測定は**構造的に案Aへ不利**である点は記録しておく: 現行
アーキテクチャでは `decide_speaker` のステップ2（声紋勝ち）で早期 return する
ため、**声紋が勝った発話の音声はクラスタに蓄積されない**。記録から見える
クラスタ音声が過小になり、案Aの鋳造が実際より遅くなる。案Aを再検討するなら
まず蓄積の仕組みから変える必要がある。

### 7.5 発話レベルの成績（GT11本平均・実質＝相槌除き）

席バグ修正（`51884b0`, §7.6）後の値:

| | 現状 | 案B即時 | 案B遅延 | 案A悲観 | 案A楽観 |
|---|---|---|---|---|---|
| 実質 | 44.1% | **53.1%** | 54.9% | 29.1% | 35.4% |
| 誤帰属 | 17.0% | 22.7% | 20.8% | 13.2% | 15.2% |
| 未確定 | 38.9% | **24.2%** | 24.3% | 57.7% | 49.4% |

案B即時の回収精度は 61%（未確定から戻った14.7ptのうち9.0ptが正解）。
案B遅延の数字が良く見えるのは「セッション全量の声紋」で測っているからで、
時系列では成立しない（§7.3）。**現状の誤帰属17%が低いのは設計の良さではなく、
席不足で誤帰属もろとも未確定に落としている副作用**なので、比較には回収精度を
見ること。

測定の限界（数字を読むとき必読）:
- 想定話者数は「実際の参加人数」を与えている（Chiba=3・実会話=2）。07-25 の
  実会話3本は上限1のまま録れた事故ラン（§20-3）で当時の constrain も統一席
  ルール以前のため、ライブ設定のままでは比較にならない
- 各セッションに「再現%」を併記（現状シナリオがライブの話者分割をどれだけ
  再現したか。最適1:1対応）。72-100%で、低い3本（142016=72%・1748=72%・
  2351=78%）は差分の信頼度も低い
- 同一人物判定はGT多数決（票数≥3・純度≥70%）＋声紋全量。どちらも満たさない
  12ペアは「判定不能」として集計から除外

### 7.9 副次的発見: マイク直の実会話ではクラスタが分裂する

実会話1723は案Bを入れても未確定84.9%が残る。主因は二重帳簿ではなく
**クラスタ分裂**——2人の会話に pyannote クラスタが10個（@diar:4=59発話・
@diar:3=41・@diar:7=26・@diar:1=19・@diar:2=11・他5個）。1641も6個。
Chiba（スピーカー再生）は3個以下なので、**マイク直の実会話に固有**の問題。

クラスタ同士の統合は §15.12/§18.9 で「分離可能な閾値なし」と結論済みだが、
§7.3 の時系列シミュレーションはその結論を追認しただけでなく、**なぜ効かないか
（短い断片は誰にでも似る／バッファの窓で答えが反転する）を機序まで特定した**。
再挑戦するなら「断片を統合する」方向ではなく、分裂そのものを減らす方向
（pyannote のパラメータ・区間の与え方・§11 選択肢b の土台交換）を先に見るべき。
