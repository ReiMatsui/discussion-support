# 採否判断への理由検討支援 実験モード

2026年11月3日 実装候補0.1。人に対する効果や実音声での動作を確認した版ではない。

## 今回の実装

日本語の3人の対面議論で、選択肢の採用・除外・候補維持を提案した発言を契機に、現在の理由と、関係する既出の理由への補足・訂正・異論を促す。基準となる提案手法v1.3の支援の中心と、無支援対手法全体の比較を維持する。

既存の脱線・事実確認・発話量に基づく声かけ・構造化・AF介入を同時に動かさない独立モードを追加した。既定の起動方法と旧モードは維持している。

## 起動

プロジェクト直下で、実験専用の設定を明示して起動する。

```sh
# 支援条件。音声認識等に必要な従来の設定に加えOPENAI_API_KEYが必要。
uv run python -m das.asr.live --study-config study/facility.json --study-condition system

# 無支援条件。同じ音声認識・話者帰属を用い、AI・共有記録の表示を停止する。
uv run python -m das.asr.live --study-config study/facility.json --study-condition none
```

別課題はstudy/event.jsonを指定する。通常の `das listen-soniox` の上位コマンドはグラフを組み立てるため、実験モードの起動には上の専用経路を用いる。まだ参加者実験を開始したものではない。

操作・録音確認用画面は従来の `/`。参加者に見せる画面は同じサーバーの `/study`。例えば既定ポートなら `http://127.0.0.1:8231/study`。使用中なら起動時に案内されたポートを用いる。研究者用画面には全文転記などがあるため、参加者には表示しない。

無支援条件の `/study` には課題名だけを出し、理由記録は出さない。共有の時計、配布資料、メモ、合意確認の手順は実験手順書に従ってそろえる。制限時間・報酬・全員の最終承認は、このモードが自動実施する機能ではない。

## 設定と入力

study内のJSONは課題名と選択肢名だけを含み、役割、個人の得点、正解、未発言の理由は含まない。session_idがpilot-unassignedのときは起動時刻から識別子を作る。本番は組・課題との対応を研究者が管理し、開始前に設定を保存する。

ASRの確定した人の発言に、記録の位置に基づく発言IDを与える。AI発言とパートナーAI発言は意味抽出の入力から除く。話者の帰属が不確かな発言は、特定個人にせず「発言者不明」とする。相づちも文脈として保持するが、相づちだけを判断使用や合意とは扱わない。

## LLMと固定処理

1. 確定転記をスナップショット化し、変更・話者訂正も含めたハッシュを作る。
2. 既存のChat Completions接続を使い、LLMが採否提案、理由、引用、検討の根拠、関連性を構造化して返す。モデルは従来と同じOPENAI_MODEL_FASTで明示して記録する。
3. 固定処理が引用、発言ID、選択肢、検討の根拠、時系列を検査する。不正な出力は採用しない。
4. 同一案の未撤回・未検討の理由を、関連性、発言時刻、IDの順に並べる。現在の理由や既検討の内容を繰り返し材料にしない。
5. 現在の理由と関連する引用から短い確認文を作る。履歴がないときの一般的な補足依頼も残す。これは効果が弱い可能性のある部分として記録する。
6. 人が話していないか、古い候補でないか、間隔・回数に達していないかを再確認して音声へ送る。会話や認識途中の入力が進めば候補を取り消す。
7. 応答も含む次のスナップショットから理由の訂正・扱いを更新し、共有表示と次の選択・抑制に使う。無応答から確認済みを推定しない。

現在の実装では、文案を自由生成する代わりに、LLMが抽出した引用と固定の短文で構成する。LLMは意味の抽出、理由の関連性、判断への使用の判定に使う。文案生成方式の実装上の具体化であり、表現の柔軟さや最適性はまだ評価していない。引用の実在を検査しても、引用の切り取りや意味判定の正しさを保証するものではない。

発話前の無音1.2秒、同じ選択肢への提示上限2回、間隔60秒は既存仕様の未検証の初期値を参照する。160字の発話長と15秒の候補有効期限は今回の試作用初期値であり、予備試行前に確認し、本実験前に固定する。理由を訂正しただけで回数をリセットしない。

## 音声出力と記録

既存の全二重LiveAgentを使い、実験時には読み上げ文を指定する。研究モードでは、指示なく生成された音声を再生しない。読み上げた実際の文と、予定した文が一致するかは実音声で点検する必要がある。人が話し始めた直後の停止は全二重の既存経路を使い、確定した人の発言が増えた時点でも停止を要求する。停止遅延やASR確定前の挙動は、今回の人工入力のテストでは確認できない。

通常の音声・転記・介入ログに加え、出力先の `.study.jsonl` に以下を記録する。

- 課題設定、条件、プロンプトのハッシュ、使用モデル。
- LLMに与えた転記の版、抽出結果、引用、提示候補、棄権理由。
- 古い出力の破棄、停止要求、予定した読み上げ文、送信の成否。

トランスクリプトを含むため研究データとして保管する。実際の音声と最終の発話文は従来の記録と照合する。送信成功を「参加者が聞いた」「有効だった」とは扱わない。

## 旧UIの操作

実験中は条件・議題・AI設定の変更、手動呼び出し、新しい会議へのリセットを拒否する。停止・開始・話者の名前登録は維持する。次の条件へ移るときは停止し、別の出力先と条件で起動する。実験中の設定変更を隠して条件を混在させない。

## 実音声で残る確認

- ASR誤り、発話の重なり、話者訂正が引用と履歴にどう影響するか。
- 実際の抽出の精度、モデル遅延、頻繁な古い出力の破棄による介入不足。
- 人の発話中に読み上げを停止できるか、再開や自由な回答が混ざらないか。
- 共有表示が訂正に追いつくか、過去の理由の短い提示が理解可能か。
- 無支援にも同じ録音と話者帰属が動き、AI支援が混入しないか。
- 参加者が理由を判断に用いるか、発話と時間だけを増やさないか。

倫理手続・外部APIへの送信条件・募集・報酬の決定は、この実装を追加したことで完了したとは扱わない。
