# 引き継ぎ: 登録者ゼロでも破綻しない話者帰属（2026-07-14）

> 作成: Claude Fable 5 (claude-fable-5), 2026-07-14。次セッションへの作業指示書。

## 1. 現状（ブランチ try/pyannote-live1、テスト63件パス）

ハイブリッド話者帰属を実装済み: Soniox=文字起こし／pyannote Live-1=クラスタリング／
声紋照合=クラスタ単位の名前付け（`_cluster_naming.py` の ClusterVoiceNamer、
`--diarization pyannote --vp-cluster-naming` で有効化）。
根拠データ: 盲検裁定2セッションで pyannoteクラスタ一貫性78% vs 現行の断片単位名前付け44%
（詳細は docs/design/pyannote_live1_trial_2026-07-09.md §8-9）。

## 2. 問題（今回の実地テストで判明）

3人の会話（YouTube動画をスピーカー再生、**声紋登録者ゼロ**、n_prof=1は本人のみ）で:
- 参加者A〜Gの7ラベルに膨張、同一人物が別人物として分裂
- 診断（transcripts/2026-07-14_1132.diag.jsonl）: ハイブリッドは動作していたが、
  (a) 登録プロファイルがないため名前付け層が無力、
  (b) 未照合クラスタがヒステリシス（累積3秒）を通過するたび「参加者X」に自動昇格、
  (c) スピーカー再生の圧縮・残響音声でクラスタ自体も割れやすい

ユーザー要件: **登録者ゼロは頻出ケースなので、この条件でちゃんと動くこと**。本質的かつシンプルに。

## 3. 設計方針（この順で実装）

登録者ゼロで提供すべき価値は「名前」ではなく**ラベルの一貫性**（同じ人が同じ参加者Xであり続ける）。
鍵は、声紋エンジンを「登録名との照合」だけでなく**クラスタ間の名寄せ**に使うこと。

1. **クラスタ間名寄せ（本質）**: 新クラスタの蓄積埋め込みを、既存の全クラスタ（名前付き＋未名の参加者X）
   の埋め込みと照合し、類似度が閾値以上なら**新規参加者を作らず既存に統合**する。
   これで (a) pyannoteのクラスタ分裂、(b) 再接続後のラベル空間変化、(c) 序盤の揺れ、が全て
   同じ機構で吸収される。ClusterVoiceNamer に蓄積埋め込みが既にあるので追加コストは小さい
2. **昇格の厳格化**: 未名クラスタの「参加者X」昇格は、名寄せで既存に統合できなかった場合のみ。
   `--diarization-max-speakers N` 指定時は参加者総数がNを超えないよう、超過分は最も近い既存参加者へ
   統合（それも不可なら未確定のまま）
3. **議事録の遡及統合**: クラスタ統合が起きたら、吸収された側の過去レコードを既存の rekey/リネーム
   機構で統合先ラベルに付け替える
4. 閾値は既存の声紋照合閾値（vp_match系）を流用し、新規定数は最小限に

やらないこと: 既存モード（Soniox単独、pyannote単独）の挙動変更、UI刷新、
オープンセット登録の高度化（masterplan §3 のスコープ管理を守る）。

## 7. 実装結果（2026-07-14、Claude Fable 5 追記）

§3 を実装完了。コミット:

- `6dc5a65` feat(live): クラスタ間名寄せ（未照合クラスタを既存クラスタの声紋埋め込みへ統合）
- `e13e50e` feat(live): flush配線にクラスタ名寄せを反映（遡及統合＋max-speakers超過時の最近傍統合）

実装の要点:

- **名寄せ（§3-1）**: ClusterVoiceNamer に `_embeddings`（canonicalクラスタ→代表埋め込み）と
  `_aliases`（吸収→canonical）を追加。`observe()` で match_profile 不成立時に
  `tracker.embed()`（新設の公開API、`_embed` へ委譲）で埋め込みを取り、他クラスタと
  コサイン比較、`tracker.dedupe` 閾値以上で統合。新規定数ゼロ（§3-4）。
- **昇格の厳格化（§3-2）**: `_recv_loop.py` の匿名キー発行を `_merged_diarization_speaker_key()`
  経由に変更（cluster_namer 有効時のみ）。名寄せ成立クラスタは canonical のキーへ帰属。
  `--diarization-max-speakers` 到達時は `nearest_cluster()`（閾値なし最近傍）の既存キーへ統合、
  不可なら従来どおり constrain で未確定。判定用に `SessionState.human_slot_budget_exhausted()` を新設。
- **遡及統合（§3-3）**: 吸収側に発行済みの @diar:N があれば既存 `rekey()` で過去レコードごと
  canonical キーへ付け替え。声紋確定名への昇格時も raw/canonical 両キーを rekey し
  `diarization_speaker_keys` を確定名へ更新（古い @diar:N の復活防止）。
- 既存モード（Soniox単独、pyannote単独）は `cluster_namer is None` 分岐で完全に従来コード。
- テスト13件追加（test_cluster_naming.py 7件、test_recv_loop_cluster_merge.py 6件、新規）。
  sandbox 検証で live スイート含む全テストパス。実機での `uv run pytest -q` は §4-1 で確認のこと。

## 8. 徹底検査と修正（2026-07-14 追記）

静的レビュー＋動的プローブ（3人会話シミュレーション、エイリアス連鎖・循環、ヒステリシス境界、
reset、エッジ入力）の二重検査を実施。正常系は健全（分裂12回でも誤統合ゼロ・ラベル乱造ゼロ、
エイリアス循環は構造的に不可能）だったが、以下を発見し修正済み:

- `b0007db` **@diar:Nキー衝突（重大バグ）**: 採番が `len(keys)+1` で、名寄せの pop により
  使用中キーが別人に再発行され得た。単調増加カウンタ `diarization_key_seq` で採番するよう修正
- `38bd1a1` **最近傍統合の下限閾値＋pending引き継ぎ**: max-speakers 超過時の最近傍統合が
  閾値なしで全く違う声（sim=0）も吸い込んでいた → `tracker.dedupe` 未満は統合せず未確定へ。
  名寄せ時に吸収側のヒステリシスpendingが捨てられ残留していた → canonical へ合算し掃除
  （`merge_diarization_pending` ヘルパ新設）
- `a6ac9e5` **軽微4件**: 初回照合で即確定したクラスタの代表埋め込みが保存されず名寄せ先に
  ならない問題／ゼロノルム埋め込みのNaNガード（`_embed`）／名寄せイベントの diag.jsonl 出力
  （`type: cluster_naming`、§4-2 の実地検証で観測可能に）／rekey の names 残留掃除

テスト8件追加（キー一意性、dedupe未満の未確定落ち、pending合算、確定時埋め込み保存、
NaNガード、diag出力、names移行）。live スイート527件グリーン。

既知の残課題（修正不要と判断、実地検証で要観察）:

- ヒステリシス3秒＜埋め込み計算5秒のため、短発話の積み上げでは最近傍統合が発動する前に
  昇格する（その後の名寄せ＋遡及rekeyで回収される設計）
- dedupe 閾値は3発話プロファイル同士で校正された値であり、20秒連結音声同士の比較では
  保守側（統合されにくい）に倒れる可能性。§4-2 でラベル総数が基準を超える場合の第一容疑

## 9. 実地テストの正解評価と constrain バグ修正（2026-07-14 追記）

§4-2 の実地テスト（3人YouTube・登録者ゼロ・max-speakers=3、transcripts/2026-07-14_142016）に
ユーザーが全82発話の正解を付与（eval/gt_2026-07-14_142016.json、作成ツールは
eval/gt_annotator_*.html、評価は eval/eval_speaker_gt.py）。結果: **帰属精度31%、未確定54%、
誤帰属15%**。分析で判明した機構（再現プローブで全観測点一致を確認）:

- 声紋自動登録キー「人物2」（=正解話者3）は resolver が正しく選んでいた（声紋一致 sim 0.75-0.85）
  のに、`constrain_human_speaker_key` の匿名キー選別が**ラベル文字の辞書順** `sorted[:max]` で、
  人物2 の文字が「参加者D」だったため全25発話が未確定に転落
- 「参加者B」の文字は、partial 表示だけで records に一度も現れない**幻キー**が占有
  （`show_partial`→`disp_name` が文字を新規割当てしていた）
- 名寄せ層（§3）自体は正常動作。誤帰属15%（話者2→参加者A混入）はスピーカー再生の劣化音声で
  クラスタ／自動登録プロファイル自体に2人分が混ざった音響条件由来で、本修正の対象外

修正（テスト531件グリーン）:

- `487d6f2` 声紋プロファイル済みキー（人物N等）は constrain のスロット選別から除外
  （登録数は tracker の set_max_human_speakers が上限管理しており二重に絞らない）
- `bb11e52` 読み取り専用の `peek_disp_name` を新設し partial 表示で文字を消費しない（幻キー根絶）
- `49bd8a0` diag に constrain 後の `final_key` を記録（今回の切り分けを阻んだ観測性の穴を解消）

再現プローブでは修正後、人物2 の全発話が一貫ラベルで通り、幻キーは消滅、上限超の匿名キーは
従来どおり未確定（constrain の本来機能は維持）。**次の実地テストで §4-2 を再実施し、
eval/eval_speaker_gt.py で再評価すること**（GT はセッション固有のため新ランには再アノテーション

- `c50d1a9` **前話者追従を全モードで帰属根拠から廃止**（ユーザー判断: 相槌は聞き手が打つ＝

## 11. フル再実験と評価方法論の修正（2026-07-14 追記）

フルパイプライン再実験（transcripts/2026-07-14_1905）は 36% と改善せず。切り分け実験で
**区切り（セグメンテーション）が支配要因**と証明: 同じ音声・同じ判定ロジックで、区切りを
初回ラン（142016）のものにすると 79%、再実験ラン（1905）のものにすると 38.5%。
Soniox の区切り・ラベル割当はラン毎に揺れ、この劣化音源では区間の16%が複数話者混在、
17%が正解範囲外になる。混在音声が声紋プロファイルを汚染し、純粋区間の判定も巻き込む。

ユーザー指摘により評価方法論も修正（`0818f5f`）: 区間単位のGTを別区切りのランに
最大重なりで移植する方式は、混在区間に単一正解を押し付けるため不正。GTを
**話者タイムライン**（誰がいつ喋ったか）として扱い、支配的話者（80%以上）が存在する
純粋区間のみ採点、混在・範囲外は件数報告に変更。この正しい方法論でも 1905 は 38%、
1729 は 41% であり、測定誤差を除いてもライブ実力は約4割（＝悲観結果は本物）。

**結論**: 判定ロジックは純粋入力なら79%（ハーネスで実証）。ボトルネックは
この音源に対するライブの区切り・ラベル品質。次の選択肢:
(a) 実会話（マイク直・本来の音響条件）で検証 — 推奨。区切り品質が本来の水準なら
    今日の改善群が効くはず
(b) 区切りの再設計 — Soniox任せでなく pyannote の話者境界で音声を切り直して声紋に
    入れる構造変更。(a) で問題が残る場合の次の手

## 12. 天井測定と最終結論（2026-07-14 追記）

選択肢(b)への投資判断のため、pyannote バッチ precision-2（最高精度・オフライン・
numSpeakers=3 指定）でこの録音を分離し、正解タイムラインで採点
（eval/score_pyannote_ceiling.py `faca78d`）:

- クラスタ3個の純度は 39% / 56% / 62% と低く、**完璧な名前付けを仮定した帰属精度の
  天井は 44%**
- ライブ再テスト（transcripts/2026-07-14_1934、スピーカー再生・実マイク）でも
  未確定50%・高速掛け合いの混在を確認。発話の半分が1秒未満

**最終結論**: スピーカー再生のYouTube高速掛け合い音源は、最高品質のバッチ分離ですら
44%が上限であり、**現在の技術スタックでは対象外**。構造変更(b)は土台が壊れているため
投資価値なし。今日の改善群（帰属ロジック79% on 純粋区間）は健全であり、
**次セッションは実会話（マイク直・本来の音響条件）での検証から始めること**。
実会話でも区切り品質が問題になる場合のみ (b) を再検討する。

正解付け（アノテーション）を再度行う場合: eval/gt_annotator_*.html の turns 埋め込みを
新セッションで再生成する。区切りが異なるラン同士の比較は eval/eval_speaker_gt.py の
タイムライン方式（§11）を使うこと。

### 15.4 Chiba 0132 初回測定とゲート判定（2026-07-16）

追加。STTラベル・声紋継続由来は従来どおり未確定。**次: 同じwavで再測**

### 15.5 相槌クラスタ帰属の再測と条件絞り込み（2026-07-16）

### 15.6 相槌枝の撤退と実質発話指標での再評価（2026-07-16）

3ラン目（transcripts/2026-07-16_1653、門番付き）: 62%/未確定25%/誤帰属12%。
撤退基準（誤帰属>8% or 精度<66%）に両方抵触したため、合意どおり
`069b91f` で本枝（2843fa4, 62cd7b1）を全revert。**結論: 相槌の帰属は

pyannoteが相槌を検出漏れすればメイン話者への吸収誤帰属、検出すれば
overlapゲートで未確定。回収するならDOA（マイクアレイの到来方向）等の
発話長非依存の信号が必要（§15.2 の議論参照）。

## 16. P1（匿名キー解決の状態機械統合）詳細設計 — 見送り（設計保存）

### 16.1 解決する問題（レビュー C1/C2/C4/C10）

現状の匿名キー解決は「発行してから constrain で落とす」順序のため:

- スロット満杯後の新クラスタは、ヒステリシス3秒消化と同時に @diar:N が
  **発行・恒久登録**され、constrain が毎回未確定に落とす（不可視キー）。以後
  「raw 未キー」が前提の最近傍統合の対象外となり**永久に未確定**（C1）。
  統合先の代表埋め込みが5秒蓄積を要する（C2）ため、初回発行の瞬間に統合が
  成立することも実質ない。handoff §3-2「超過分は最近傍へ統合」は未達のまま。
- 相槌もヒステリシス pending に加算され、相槌の積み上げだけで @diar:N が
  発行され得る（C4）。
- 最近傍統合が成立しても永続化されず、毎発話再計算で別participantへ振れ得る（C10）。

### 16.2 新設計: 「発行前に判定する」1本の流れ

対象は **cluster_namer 有効時（ハイブリッド構成）のみ**。Soniox単独・pyannote単独
（cluster_namer なし）の経路はコードごと従来のまま（本節の変更を通らない）。

_recv_loop._merged_diarization_speaker_key を以下の状態機械に置き換える:

```
未キー raw の解決（1発話ごと）:
 0. 相槌(_is_backchannel)・重なり(cluster_overlap) → pending に加算せず UNSURE
    （C4。従来も record は UNSURE になるので表示上の挙動差はほぼ無し。
     diag の key フィールドが UNSURE になる点だけ変わる）
 1. canonical = namer.canonical_cluster(raw)。名寄せ成立済みなら canonical の
    キーへ（pending 合算・遡及 rekey 含め現行踏襲）
 2. canonical に既キーあり → それを返す（現行踏襲）
 3. pending += duration_ms。pending < 3000ms → UNSURE（現行踏襲）
 4. スロットに空きあり（not human_slot_budget_exhausted()）
    → @diar:N を発行（pending 消化。現行と同じ採番）
 5. スロット満杯:
    a. nearest_cluster() の sim >= namer.merge_sim かつ相手に既キーあり
       → そのキーへ統合し **diarization_speaker_keys[raw] = nearest_key を
         永続記録**（C10。以後この raw は 2. で即解決）
    b. 不成立 → **キーを発行せず** UNSURE。pending は threshold で頭打ちにして
       保持し、後続発話（相手の埋め込みが5秒蓄積で育った後）に 5a を再試行
       （C1/C2 の解消点: 「発行できないときは待つ」）
```

constrain_human_speaker_key は最終ゲートとして現行のまま残す（closed roster・
profiles 素通し・max 途中変更時の落とし）。通常フローでは「発行時点でスロット
判定済み」のため、constrain が @diar を落とすのは max を会議中に減らした場合等に
限られるようになる。辞書順スロット選別（C5）の廃止は本変更のスコープ外
（実害経路が P1 でほぼ消えるため、実会話検証後に判断）。

### 16.3 変更ファイルと規模

- _recv_loop.py: _merged_diarization_speaker_key の順序再編（約30行）
- _session_state.py: key_for_diarization_speaker に「発行せず pending 保持」を
  指示する引数（allow_new=False 相当）を追加（約10行）。

### 18.10 オフライン最適化第2弾: 持続性ルールの棄却と strict_sec 2.0（2026-07-22）

**(2) 14データセット分割sweep → strict_sec 3.0→2.0 を採用 `71e5da5`。**

## 19. 介入の同一内容再表示バグの修正（2026-07-22、Claude Fable 5）

**報告（実利用）**: 時間を置くと同じ介入表示が何度も出る。
（本ドキュメントの主題＝帰属側ではなく介入側だが、明示の修正依頼を受けた）

**原因**: 介入の再発火抑止が時間（cooldown 25s等・kind別/global）しか
見ておらず、**内容を比較する層がどこにも無かった**（fact の checker 側
90s dedup が唯一の例外）。会話が停滞すると checker は同じ入力窓から同じ
brief（脱線理由/整理焦点）を再生成し、cooldown 経過後にそのまま再発火。
文案生成 LLM にも過去介入は渡っておらず、表示層にも dedup なし。

**修正（2層）**:

1. `7b7dd40` **Controller に duplicate_content 門番**。brief が内容そのもの
   である drift/summarize に限り、直近の同種介入と実質同一
   （空白除去後の完全一致 or SequenceMatcher 類似 ≥ 0.6 =
   `_INTERVENTION_CONTENT_DEDUP_SIM`）の候補は 10 分窓
   （`_INTERVENTION_CONTENT_DEDUP_SEC`）で採らない。抑止された
   drift/summarize の pending は忘れる（毎tick再抑制の防止）。
   `_recent_interventions` deque は 10→30 件（窓の照会範囲を担保）。
   fact は checker 側 90s dedup の責務のまま。silence/invite/retry の
   brief は内容ではないため対象外（silence は pending>0 が発火条件なので
   新規発話なしには出ない）。
2. `61bfa60` **生成側への注入**。drift/summarize/silence/invite の
   trigger に直近のファシリテーター発話（records 末尾4件）を渡し、
   「同じ内容の発言を繰り返さない」注記を付ける。brief が違っても
   文面が実質同じになる再発への第2層。fact/manual/retry は不変。

**検証**: 新規テスト12本（controller 9 + realtime 2 + worker helper 1）、
全量 891 passed（既知flake `test_structuring_checker_rejudges_after_pending_reset`
のみ除外、修正前後とも失敗することをstashで確認）。ruff 新規エラーなし。
帰属側（flush/_attribution）は非接触なので replay 基準表（§18.10）は不変。

**残る再発余地（既知・許容）**: 同一内容でも 10 分窓を過ぎれば再発火し得る
（永久封印は「本当にまた脱線した」場合を殺すため意図的にしない）。silence
要約は内容比較をしないが、第2層の注記が繰り返しを抑える。ライブでの
効きは次回実会話で `intervention_review.jsonl` の duplicate_content 抑止
行を確認。

したがって §24.3 の判断（項目2の決着には新形式の記録が要る）は変わらない。
ただし**見るべき数字と比較の基準はこの表で確定した**——新しい記録1本で
同じ指標を測り、1.0倍近傍なら土台は健全（改善は声紋層・門番側）、
2倍を大きく超えるなら分裂が支配的（入力側の問題）と判断できる。

測定は `eval/diagnose_live_session.py` の B 節。旧ランでも下限モードで

## 25. 文字起こし精度の初測定（2026-07-25、Claude Opus 5）

**このプロジェクトで初めて、実会話に対する文字起こし（テキスト）の精度を測った。**
これまで eval/ の採点はすべて「話者ラベルが正しいか」で、テキストの正確さは
合成テストセット（scripts/score_overlap_test.py の difflib 類似度）でしか
測られていなかった。「精度よく文字起こしできる」が目的である以上、そこに
改善のループが無いのは穴だった。

### 25.1 材料は既にあった（新規録音もAPIコストも不要）

- 参照: `transcripts/<conv>.turns.jsonl` — `eval/prep_chiba.py` が Chiba3Party の
  形態論CSV（時刻つき）から生成した GT定義セッション。話者・時刻・**本文**を持つ
- 仮説: `transcripts/<run>.turns.jsonl` — 同じ会話をシステムに流した出力
- 対応: `eval/gt_<run>.json` の `transplanted_from`

Chiba 13ランが対応づく。Sakura の生データ（`data/sakura_raw/*.cha`）と CallHome も
本文を持つので、同じ枠組みを広げられる（未実施）。

### 25.2 結果（Chiba 13ラン・CER）

| 指標 | 値 |
|---|---|
| CER（フィラー込み） | 平均 **32.3%**（16.2〜38.2%） |
| CER（フィラー除き） | 平均 32.0% — **フィラーは主因ではない** |
| 取りこぼし率 | 平均 **1.2%**（0.1〜3.6%） |
| 長さ比（出力÷参照） | 平均 0.83 |

読み:

- **取りこぼしが1.2%と極めて低い**。VAD・区切り・重なりで発話を落とす問題は
  ほぼ無い。CER の中身は「拾えなかった」ではなく「文字が違う」
- **長さ比0.83＝削除寄り**。参照より17%短い。転記記号を除いた後も短いので、
  語尾・延伸・短い相槌あたりが落ちていると見られる
- **CER 32% は表記ゆれを多く含む**。目視すると「わたし→私」「くさい→臭い」など
  漢字/かなの差が大量にある。参照は話し言葉の転記規則でかな寄り、Soniox は
  漢字を当てる。**「理解できたか」という意味での精度は 32% が示すより良い**
- 会話差が大きい（0132=16.2% 〜 0532=38.2%）。0132 は §18.6 で「コーパス内では
  易しい側」と判明している会話で、帰属精度の傾向と一致する

### 25.3 測り方（と、失敗した「改善」の記録）

既定は**全文連結**での CER。当初「参照は相槌を独立ターンとして挟むのに対し
システムは長くまとめるので、全文連結では順序ずれが誤差に化ける」と考えて
開始時刻10秒窓を試したが、**CER は 32%→50% と悪化した**（chiba0132 は
16%→75%）。原因は逆で、システムのターンが40秒級に長く1つが複数の窓をまたぐため、
参照だけが後続の窓に残って全削除に数えられる。**窓で仕切ると「区切り方の違い」が
「認識の誤り」に化ける。** 既定を全文連結に戻した（`--window` は残してあるので
区切りの一致度を見たいときには使える）。同じ「改善」を繰り返さないようテストで固定。

### 25.4 次にできること

- **表記ゆれの分離**: 参照の形態論CSVには読み（`pron` 列）がある。システム出力を
  かなに変換できれば読みベースの CER が出せ、「表記の違い」と「聞き取りの誤り」を
  分離できる。形態素解析器の導入が要る（未着手）
- **STT の比較**: `--stt speechmatics` の配線はあるのに一度も比較されていない。
  同じ会話で CER を測れば選択の根拠になる
- **Sakura / CallHome への拡張**: 生データに本文があるので、`prep_chiba.py` と
  同じ変換を書けば対面4人・電話8kHz の CER も測れる

## 26. 帰属損失の原因分解と、蓄積中への門番拡張の根拠（2026-07-26、Claude Opus 5）

### 26.1 なぜ分解したか

「実質○%・誤帰属○%・未確定○%」の総量だけを見てきたため、改善の優先順位が
「たぶんこれが効きそう」の域を出なかった。`eval/decompose_attribution.py`
（新規）は GT 付きランの1発話ごとに結末を判定し、未確定を**発生した層**で、
誤帰属を**声紋層の kind** で分ける。上限（その原因を完全に潰したら最大何pt
返るか）が読めるので投資先を数字で選べる。APIコストは0（既存の記録のみ）。

### 26.2 結果（現行コードの9ラン・2026-07-20・相槌を除く実質発話が分母）

```
正解 54.4% / 誤帰属 16.3% / 未確定・席落ち 11.8%
                       / 未確定・ラベル不純 11.8% / 未確定・蓄積待ち 5.6%
```

誤帰属の kind 別内訳（GT付き14ラン通算）:

```
ラベル不純 41.4% / ラベル継続 27.7% / 蓄積中 21.4% / 補正 3.0% / 声紋一致 2.1%
```

**誤帰属の 90.5% は「声紋層が自信を持てなかった発話」から出ている。**
高信頼4種（声紋一致・補正・自動登録・合流）由来は約5%しかない。
つまり打つべき手は声紋照合の精度向上ではなく、**自信の無い発話をどう扱うか**。

### 26.3 §18.8 の門番は誤帰属の 41% にしか掛かっていない

§18.8 の不純回収門番は kind「ラベル不純」だけを対象にしている。その
docstring は範囲を広げなかった理由をこう書いていた——「これらは Chiba
12会話の測定で誤帰属の主因ではなく、遮断の効果を測ったデータもないため
広げない（データなき拡張はしない）」。26.2 はその**欠けていたデータ**である。
`ラベル継続`(27.7%) + `蓄積中`(21.4%) = **誤帰属の 49.1%** が門番の外にある。

### 26.4 裏付けの弁別力（採否はここで決まる）

成績の増減より先に見るべきは「裏付け（その発話自身の声紋1位候補が回収先と
一致し sim ≥ 0.25）が正解と誤帰属を分けるか」である。9ラン・実質発話:

| kind | 裏付け | 正解 | 誤帰属 | 未確定 | 正解率 |
|---|---|---:|---:|---:|---:|
| 蓄積中 | あり | 12 | 1 | 0 | **92%** |
| 蓄積中 | なし | 2 | 29 | 54 | **6%** |
| ラベル継続 | なし | 38 | 35 | 65 | 52% |

**蓄積中では裏付けがほぼ完全な弁別子**（§18.8 が ラベル不純 で見つけた
37/6 対 21/72 より強い）。遮断で失う正解は2件、潰せる誤帰属は29件。

**ラベル継続では裏付けが原理的に成立しない**——138件すべてで `name` が
記録されていない（この kind では声紋の1位候補が diag に残らない）。
したがって「ラベル継続に門番を広げる」は門番ではなく**全遮断**であり、
§18.8 が「正解回収を失いすぎる」として退けた列と同じものになる。
`--gate-kinds` はこれを自動で見抜いて警告を出す。

### 26.5 反実仮想（開発5本/検証4本、§18.8 と同じ作法）

`uv run python eval/decompose_attribution.py --all --prefix 2026-07-20
--gate-kinds 蓄積中 --split 5`

| セット | 正解 | 誤帰属 | 未確定 |
|---|---|---|---|
| 開発5本 | 53.3%→53.2% (-0.1pt) | 21.6%→18.4% (**-3.1pt**) | 25.1%→28.4% |
| 検証4本 | 55.8%→55.8% (±0.0pt) | 9.7%→7.1% (**-2.7pt**) | 34.4%→37.1% |

検証セットで**正解の損失が0**。過学習の余地も無い——閾値0.25も述語も
§18.8 が ラベル不純 で決めたものをそのまま使っており、新しい自由度を
一つも導入していない。

参考: `ラベル継続` 単独は 正解 -5.9pt / 誤帰属 -5.5pt（誤帰属1点に正解1.09点）。
両方に広げると 正解 -6.1pt / 誤帰属 -9.8pt。**蓄積中のみが採るべき手**。

### 26.6 実装前に決めるべき論点（未着手・要承認）

測定は「裏付けの無い蓄積中の発話を、経路を問わず未確定にする」を仮定して
いる。一方 §18.8 の門番はステップ3d＝**diarization が勝った経路にだけ**
掛かる。この9ランの `records`/`diag` には `speaker_source` が残っていない
ため、31件の内訳（3d の対象か、ステップ4の STT フォールバックか）は
オフラインで復元できない。したがって:

- **3d に限定して広げる**なら、効果は上表の一部分（上限が -3.1pt/-2.7pt）
- **経路を問わず掛ける**なら上表どおりだが、ステップ4も変わる

どちらも `s.cluster_namer is not None` を条件にすればハイブリッド構成のみに
閉じ、pyannote単独・Soniox単独は不変（§18.8 と同じ境界）。

副次的に、`diag` に `speaker_source` を残せば次回からこの内訳が測れる
（診断のみ・挙動不変）。

### 26.7 ラベル継続の `name` 欠落は別件の宿題

27.7% の誤帰属を抱える `ラベル継続` に対して打つ手が無いのは、弁別に使える
情報が記録されていないからである。`_classify` がこの kind を返すとき1位候補と
sim を残せば、蓄積中と同じ形の門番が設計できる可能性がある。ただしそれは
**声紋層の変更**であり、まず「残す」だけ（診断のみ・挙動不変）を先にやって
データを取るのが筋。

### 26.8 承認を受けて入れた記録（2026-07-26、挙動変更は無し）

26.6/26.7 の判断としてユーザーが選んだのは**両方とも「まず記録だけ」**。
入れたのは次の2点で、いずれも判定を一切変えない。

1. `speaker_source` を diag へ（`src`/`why`。`20f7511`）。records にしか
   無く終了時に失われていたため、誤帰属が 3d の対象経路か STT フォールバック
   かを分けられなかった。
2. 短発話経路の「ラベル継続」で 1位候補と sim を `_note` に渡す（`cea2790`）。
   照合はしているのに `**info` を渡しておらず捨てていた。`tracker.last` の
   `name` を読む側は kind で分岐している（自動登録・ラベル不純）ため不変。

残る43件は kind「照合なし」＝埋め込みを計算していない経路なので、記録では
埋まらない。計算させるのは挙動変更なので別途判断する。

**次のラン以降**、`--gate-kinds ラベル継続` の裏付け表が意味を持つようになり、
蓄積中への門番拡張も「3d 限定で何pt か」を数字で切り分けられる。それまでは
26.5 の値が上限、3d 限定はその一部分、という理解でよい。

## 27. 未確定の正体はクラスタ分裂だった（2026-07-26、Claude Opus 5）

「精度を上げると同時に未確定も減らしたい」という要求に対し、どの打ち手が
**トレードオフでないか**を切り分けた。結論から言うと、未確定の最大塊は
判定の弱さではなく**クラスタ分裂**であり、ここだけは精度と未確定を同時に
改善できる。APIコストは0（既存の記録と .wav、ローカル ReDimNet のみ）。

### 27.1 席落ちは「回収すれば正解になる」ものではなかった（見立ての訂正）

§26 の分解で未確定の最大塊は「席落ち」（上流はキーを決めていたのに
constrain＝参加人数上限で落ちた分）11.8% だった。当初これは帳簿の問題＝
回収すれば正解が増える、と見ていた。**測ったら逆だった。**

`--seat-recovery`（constrain 前のキーをそのまま採る）:

```
正解 54.4%→55.1% (+0.6pt) / 誤帰属 16.3%→27.5% (+11.1pt) / 未確定 29.2%→17.5%
```

落ちた158件は**全て `@diar:N`**、つまり席を得られなかった pyannote クラスタ。
そのまま通せば「別の参加者」として表示されるだけなので、未確定が誤帰属に
化ける。constrain は分裂クラスタのフィルタとして**正しく働いていた**。

### 27.2 必要なのは「通す」ことではなく「寄せる」こと

`--merge-ceiling`（分裂クラスタを多数派話者の席へ統合した場合の上限。GT使用）:

```
正解 54.4%→63.5% (+9.1pt) / 誤帰属 16.3%→19.0% (+2.7pt) / 未確定 29.2%→17.5% (-11.8pt)
```

**9ラン全てで改善**。しかも正解が上がり未確定が下がる。§26.5 の門番拡張
（誤帰属 -2.7pt と引き換えに未確定 +2.7pt、正解はほぼ不変）が純粋な交換
だったのに対し、名寄せは交換ではない。**優先順位はここで決まった。**

落ちたクラスタ21個は**全て「既に席を持っている話者」のもの**だった
（新しい人が来たのではなく、同じ人が割れている）。純度90%以上は10個で、
残り11個は50-89%（大きいクラスタほど不純）。上限が +9.1pt に留まるのは
この不純分のため。

### 27.3 声紋で寄せ先を当てられる（`eval/cluster_merge_feasibility.py`）

上限は GT を使った値なので、そのままでは投資判断に使えない。実際の名寄せは
声紋で決めるので、「**寄せ先を当てられるのか**」を測った。各分裂クラスタの
音声（上限30秒連結）を、席持ちキーの実音声と突き合わせる:

```
1位正解率  クラスタ単位 19/21 = 90% / 発話重みつき 149/158 = 94%
```

**当てられる。**しかも大きいクラスタほど sim が高い（1655 の36件=66秒は
0.92、1709 の30件=27秒は 0.83、1738 の18件=21秒は 0.85、2351 の19件=16秒は
0.81）。いずれも確定しきい値 0.65 を大きく超えている。

### 27.4 では live でなぜ確定しなかったのか（2つの原因）

1. **蓄積下限に届かない**: 21個中13個が `PYANNOTE_CLUSTER_NAMING_MIN_SEC`
   (5秒) 未満で、live では**照合を試みてすらいない**。ただしこの13個は
   発話にすると31/158件（20%）にとどまる。
2. **参照側が人物プロファイル**: 残り8個（発話127/158＝80%）は5秒以上あり
   照合は走っている。にもかかわらず確定しなかった一方で、**席の実音声と
   比べると 0.78-0.92 と余裕で確定線を超える**。差は参照側にある——
   `ClusterVoiceNamer` は `VoiceProfiles.match_profile()` すなわち
   **人物プロファイル**（短窓の登録サンプルから作られる）に照合しており、
   席が実際に喋った音声そのものとは比べていない。

`_cluster_naming.py` の docstring は「分裂しても両方が同じ人物へ照合される
だけなので実害は無い」と書いているが、**これは測定で否定された**。分裂した
側は照合に失敗して匿名 `@diar` キーになり、席上限で落ちる。

### 27.5 次の一手（未着手・要承認）

原因2が発話数の80%を占めるので、本命は**参照側をクラスタ代表音声にする**
（クラスタ対クラスタで比べる）こと。原因1（蓄積下限）は残り20%で、下限を
下げるのは短音声の誤確定を増やすため単独では危険。

いずれも `_cluster_naming.py` の挙動変更なので、着手前に承認を取る。

**検証手段の訂正**: 当初「既存9ランの再生で足りる」と書いたが誤り。
`eval/replay_live_attribution.py` はクラスタ層の入力（diarization の窓）を
必要とし、それを diag に残す変更（§23, `8c4353c`）は 2026-07-25 なので、
2026-07-20 の9ランには `diar` フィールドが無い。したがって:

- **設計の当たり判定**は 27.3 のオフライン測定で足りる（既存 .wav のみ）
- **端から端までの検証**には新形式の録音が要る。全12会話は不要で、分裂の
  影響が大きい3本で十分: 1655（36件=66秒の分裂、上限 +19.0pt）、
  1738（+12.2pt）、1748（分裂5個、+11.2pt）

### 27.6 §26.5 の門番拡張の位置づけ（後退）

蓄積中への門番拡張は「誤帰属 -2.7pt / 未確定 +2.7pt / 正解 ±0」の純粋な
交換であり、未確定も減らしたいという要求とは逆を向く。名寄せ（27.2）を
先にやると未確定が11.8pt下がるので、その後に改めて要否を判断する。
**保留**とし、実装しない。

### 27.7 §15.12 は正しかった——安全性を担っているのは閾値ではなく適用範囲

27.3 の測定を受けて「参照を人物プロファイルからクラスタ代表音声に変える」
実装に入る直前、`_cluster_naming.py` の経緯コメントで、それが §15.12/§18.9
で**測定のうえ削除された機構そのもの**だと気づいた。§15.12 の根拠は
「クラスタ埋め込み同士の比較は別話者間で 0.707 まで出る一方、同一人物の
再統合は 0.52 ＝ 同一/別人を分離できる閾値が存在しない」。

**自分のデータで確かめたら、§15.12 の再確認になった。** 各分裂クラスタの
「2位」は定義上つねに別人なので、その分布が別人simの実測になる:

```
別人との類似度（n=21）: 最大 0.89 / 上位 0.89 0.83 0.65 0.61 0.59
確定しきい値(0.65)以上が3件
```

**別人が 0.89 に達する。**したがって 27.3 の 90%/94% は「0.65 を超えたから
当たった」のではなく、**席持ちの中の1位を選んだから**当たった。絶対しきい値
による開集合の判定（このクラスタは既存の誰かか、それとも新しい人か）は、
§15.12 のとおり今でも不可能である。

**では何が安全性を担うのか**: 適用範囲である。ここで扱う158件は
**constrain が席上限で落とした発話**、つまり「参加人数の宣言上、新しい
参加者ではありえない」状態のクラスタに限られる。開集合の判定が要らない＝
§15.12 が壊れた場所を通らない。閉集合の割当て（席持ちN人の中で1位）は
成立する、というのが今回の測定の内容。

成績（席落ちクラスタのみに適用）:

| 規則 | 正解 | 誤帰属 | 未確定 |
|---|---|---|---|
| 1位＋sim≥0.65 | +8.1pt | +2.3pt | -10.4pt |
| 1位のみ（下限なし） | **+8.8pt** | +3.0pt | **-11.8pt** |
| （GT を使った上限） | +9.1pt | +2.7pt | -11.8pt |

下限を付けても付けなくてもほぼ同じ＝**しきい値は効いていない**という
事実が、上の結論を裏側から支持している。増える誤帰属（+2.3〜3.0pt）は
寄せ先の間違いではなく、分裂クラスタ自体の不純（50-89%）が持ち込む分。

**設計上の帰結**: 実装するのは「クラスタ間名寄せの復活」ではなく、
`constrain` が席を与えられないクラスタに対する**席の割当て規則**である。
`_cluster_naming` の確定（不可逆・全発話に波及）ではなく、
`constrain_human_speaker_key` が未確定を返す場面での**その発話限りの選択**
として置けば、§15.12 の「不可逆な操作は高確信を要求」という一般則とも
衝突しない。

### 27.8 実装: 席落ち発話の割当て（2026-07-26、`5d81b34`。挙動変更）

ユーザー承認のもと実装。置き場所は `_cluster_naming` の確定ではなく、
`RecvLoop.flush` で `constrain_human_speaker_key` が未確定を返した直後。
新モジュール `_seat_audio.py`（`SeatAudio`）が席ごとの実音声を持つ。

**適用条件**（すべて満たすときだけ動く）:

- ハイブリッド構成（`seat_audio` は `--vp-cluster-naming` かつ tracker 有効
  のときだけ生成）。pyannote単独・Soniox単独は不変
- 相槌でない
- 上流（`decide_speaker`）はキーを決めていた（未確定なら席の問題ではない）
- `constrain` が未確定に落とした
- 参照が3秒以上ある席が2つ以上ある

**やらないこと**: 確定を書かない。台帳（`diarization_speaker_keys`）にも
`_cluster_naming._confirmed` にも触れない。次の発話は独立に判定される。

**因果的な実測**（参照を「その時点までの過去の音声」だけで作った値。
GT は採点にしか使っていない）:

| | 正解 | 誤帰属 | 未確定 |
|---|---|---|---|
| 現状 | 54.4% | 16.3% | 29.2% |
| 割当てあり | **61.9%** (+7.5pt) | 20.6% (+4.2pt) | **17.6%** (-11.7pt) |

9ラン全てで正解が上がる。増える誤帰属は寄せ先の間違いではなく、分裂クラスタ
自体の不純（純度50-89%）が持ち込む分。

**未来を見た値との差**: 27.3 の 94%（クラスタ単位）・89%（発話単位）は参照を
セッション全体から作っており楽観。因果的には1位正解率 63-65% に落ちる。
序盤は席の参照が薄いのが主因。**この差は必ず因果版で確認すること。**

**`SEAT_AUDIO_MIN_REF_SEC` の校正**（候補から外す下限。値は 3.0）:

| 下限 | 適用 | 1位正解 | 正解 | 誤帰属 |
|---|---:|---:|---:|---:|
| 0秒 | 157 | 63% | +7.5pt | +4.2pt |
| 3秒 | 153 | 65% | +7.4pt | +3.9pt |
| 12秒 | 93 | 71% | +4.8pt | +2.2pt |

0〜8秒はプラトーで**値は効いていない**。12秒以降は精度が上がるが適用が6割に
減って取り分が半減する。したがってこれは成績のつまみではなく「数秒しか
聞いていない席には寄せない」という下限。プラトーの内側なので過学習も無い。

なお下限は「全席が育つのを待つ」ではなく「育っていない席を候補から外す」。
待つ形にすると、たまにしか喋らない人が1人いるだけで適用が157→17件に落ちる
（最初の測定で踏んだ誤り）。

**残る宿題**: (1) 新形式の録音（1655/1738/1748）での端から端までの確認、
(2) 誤帰属が +4.2pt 増える分——寄せ先ではなく分裂クラスタの不純が原因なので、
効くのは区切りの整列（§11 選択肢b）であって割当ての調整ではない。

### 27.9 記録だけで検証できた（新規録音は不要だった）

ユーザーの指摘「手持ちのデータと正解で確認できないのか」を受けて検討し直した
結果、**この機能に限っては新規録音が要らない**と分かった。理由は機能の性質:
台帳にも `_cluster_naming._confirmed` にも何も書かず判定が1発話で閉じるので
下流への影響が無く、必要な入力（上流キー・constrain の結果・音声・席の参照）が

### 27.10 参照は高信頼の発話だけで作る（`e0c7f2a` 相当の修正）

誤帰属の増分 +3.9pt を追ったところ、**1635 に集中**していた（15件寄せて的中1件、
そのランだけ誤帰属 +11.2pt。他8ランは的中 102/138 = 74%）。

**ただし 1635 は直らなかった**（15件寄せて的中1件のまま）。このランでは

2位との差も 0.12-0.43 と大きく、余裕を課しても防げない。

残る誤帰属の主因は分裂クラスタ自体の不純なので、効くのは区切りの整列

### 27.11 席の音声による再判定を2か所に広げた（2026-07-26、挙動変更）

目標は「正解8割」。62% からの続き。手持ちの記録だけで2つの拡張を測り、
両方入れた（`eval/seat_assign_extensions.py`。本番の `SeatAudio` を駆動）。

**A. 「ラベル不純」で棄権した発話も席の音声で判定する**
未確定の主因がこれ。棄権の理由は人物プロファイルとの照合が弱かったことで、
参照を席の実音声にすれば分離が良くなる（§27.4 と同じ理屈）。

**B. 「蓄積中」に §18.8 の裏付け門番を掛け、切った先を A が拾う**
門番単独は「誤帰属 -2.7pt と引き換えに未確定 +2.7pt」の交換で、§27.6 で
一度**保留にした**。拾い直す先ができたので純増に変わった。

| 条件 | 正解 | 誤帰属 | 未確定 |
|---|---|---|---|
| いま（席落ちのみ） | 62.0% | 19.7% | 18.3% |
| A のみ | 70.3% | 22.4% | 7.3% |
| B のみ | 62.7% | 17.1% | 20.2% |
| **A+B** | **71.0%** | **19.7%** | **9.3%** |

**A+B が効くのは、B の門番が A の増やす誤帰属をちょうど相殺するから**
（A単独 +2.6pt、B単独 -2.7pt）。正解 +9.0pt を誤帰属の増加なしで取れる。
開発5本/検証4本に分けても成立（検証は 63.6%→76.9%、誤帰属 -0.3pt）。

**実装**: 裏付けの述語は `_attribution.voiceprint_endorses` に集約し、
§18.8 の3d門番と共用する（二重定義を作らない）。B は3dより適用範囲が
広い（経路を問わない）——そう測ったからで、3d限定にすると測定値と意味論が
ずれる。A は `flush` の割当て条件に `kind == "ラベル不純"` を足すだけ。

**リスク**: A は席上限に達していない場面でも動くので、§27.7 の「開集合の
判定は不可能」という制約に触れる。新しい参加者の最初の発話が既存の席へ
吸収されうる。ユーザー判断で「人数設定に気をつければよい」として受容。

**残り**: 正解71%・誤帰属19.7%・未確定9.3%。8割まであと9pt で、未確定を
全部正解にしても届かない。**次は誤帰属を削る番**で、主因は分裂クラスタの
不純だから、効くのは区切りの整列（§11 選択肢b）。

### 27.12 ラベルしか根拠が無い判定は席の音声で決め直す（2026-07-26、正解79.2%）

目標「正解8割」に対する到達。A+B（71.0%）の残り誤帰属252件を内訳で見たら
**48%が kind「ラベル不純」で上流のキーがそのまま誤っていた分**だった。
A は「棄権した分」しか拾っていなかったが、ラベル不純は**決めていた分こそ
当てにならない**——そのSTTラベルが複数人を混載していると分かっているのに、
そのラベルに基づくキーを通していた。

そこで `_LABEL_ONLY_KINDS = {ラベル不純, ラベル継続}` を導入し、この2種は
上流のキーを信用せず席の実音声で決め直す。ラベル継続も同類（声紋照合が
成立せず、ラベルの過去の対応を引き継いでいるだけ）。

| 条件 | 正解 | 誤帰属 | 未確定 |
|---|---|---|---|
| 席落ちのみ（§27.8） | 62.0% | 19.7% | 18.3% |
| A+B（§27.11） | 71.0% | 19.7% | 9.3% |
| +C ラベル不純を上書き | 76.8% | 13.9% | 9.3% |
| **+D ラベル継続も** | **79.2%** | **13.6%** | **7.1%** |

開発5本 77.1% / 検証4本 **82.0%**。**正解と誤帰属と未確定が同時に改善する**
（C以降は誤帰属も下がる）。

**なぜ効くのか**: 「ラベルに基づく推測」より「声を直接比べる」ほうが強い、
というだけ。席の実音声という良い参照ができて初めて成立した（人物プロファイル
相手では §27.4 のとおり分離が足りない）。声紋で決まった判定（高信頼4種）は
上書きしない——そちらは席の平均より強いため。

### 27.13 §11 選択肢b（区切りの整列）は割に合わない（測定で判明）

「次は誤帰属を削る番、本命は区切りの整列」と書いたが、**測ったら小さかった**。
`eval/segment_boundary_ceiling.py`（新規）で Soniox の区切りが GT の話者境界を
またいでいる割合を測ると:

```
またぎ 316/1202 = 26%（発話数）／失う時間 5.9%
当時の誤帰属200件のうち、またぎが絡むのは 44件 = 22%
```

またぎ自体は多いが、少数派側の時間はわずかで、誤帰属の8割はまたぎと無関係
だった。§11 選択肢b を完璧にやっても誤帰属 19.7%→15.4% 程度。構造変更の
規模に見合わない。**当面は着手しない**（判断を覆すには、またぎの多い別
ドメイン——対面4人・重なり35%級——での再測が要る）。

代わりに効いたのが 27.12 で、こちらは誤帰属を 19.7%→13.6% に下げている。

**次の材料**（+C 適用後に残る誤帰属182件の内訳）:

```
seat_assign 51% / ラベル継続 20% / ラベル不純 13% / 声紋一致 5% / 補正 5%
```

過半が**席の割当て自体の誤り**になった。つまり次に効くのは「寄せ先の選び方」
の改善（参照の作り方・比較の仕方）であって、上流の帰属ロジックではない。

### 27.14 寄せ先の選び方は現状が最良だった（否定的結果・2026-07-26）

§27.12 の時点で残る誤帰属の51%が「席の割当て自体の誤り」だったので、
参照の作り方を変えて改善を狙った（`eval/seat_pick_variants.py`）。
いまの実装は席あたり**1本**の埋め込み（先頭30秒を連結して凍結）で、
連結は声の幅を1点に潰すから不利ではないか、という仮説だった。

| 選び方 | 正解 | 誤帰属 | 未確定 |
|---|---|---|---|
| **single（いまの実装・30秒連結1本）** | **78.5%** | **16.3%** | 5.2% |
| multi（発話ごとに保持・最大類似） | 77.6% | 17.2% | 5.2% |
| top2（上位2本の平均） | 78.0% | 16.8% | 5.2% |
| asnorm（席ごとの当たりやすさを正規化） | 78.0% | 16.8% | 5.2% |

**どれも現状を超えない**（開発・検証のどちらでも同じ順序）。連結して平均化
することが不利、という仮説は否定された。むしろ平均化がノイズを均している。

したがって残る seat_assign の誤りは参照の作り方が原因ではない。1635 の例
（正解席の参照は純度100%なのに別人に寄る、§27.10）と同じで、**声紋そのものが
その話者対を分離できていない**とみるのが自然。ここを動かすなら埋め込みモデル
の変更（他モデルとの比較）か、単発の発話ではなく文脈（同一クラスタの発話を
まとめて投票する等）を使う方向になる。

**この節は否定的結果の記録**である。同じ仮説で再挑戦しないために残す。

### 27.15 文脈を足すと悪化する（否定的結果・2026-07-26）

「1発話より複数発話をまとめたほうが埋め込みが安定する」（§27.3 でクラスタ
単位94% 対 発話単位89%）を根拠に、席と比べる**問い合わせ音声**へ過去の
文脈を足してみた（`eval/seat_query_context.py`）。遅延は増えない設計
（過去の音声しか使わないので、まとまるのを待たない）。

| 問い合わせ音声 | 正解 | 誤帰属 |
|---|---|---|
| **own（いまの実装・その発話だけ）** | **78.5%** | **16.3%** |
| label（同じSonioxラベルの過去10秒を足す） | 64.0% | 30.8% |
| key（同じ上流キーの過去10秒を足す） | 70.8% | 24.0% |
| label_w（labelを直近30秒に限る） | 66.8% | 28.0% |

**大幅に悪化する。** 開発・検証のどちらでも順序は同じ。

**理由**（これが一般則として残る）: 再判定が必要な発話は、まさに
**まとめる基準が壊れている発話**である。ラベル不純はそのラベルが複数人を
混載しているという意味だし、席落ちクラスタは分裂しているクラスタそのもの。
壊れた信号でまとめれば、別人の声が問い合わせに混ざって誤りが伝播する。
**壊れた信号を使って壊れた信号を直すことはできない。**

§27.3 の「クラスタ単位94%」が良く見えたのは、GT でクラスタ所属を定義し、
セッション全体の音声を使った非因果的な測定だったから。実運用の条件では
成立しない（§27.8 で因果版が 89%→63% に落ちたのと同じ性質の楽観）。

**この節は否定的結果の記録**である。同じ仮説で再挑戦しないために残す。

### 27.16 埋め込みモデルを大きくしても割に合わない（2026-07-26）

残る誤帰属の過半が「席の音声と比べて寄せ先を選ぶ」段の誤りなので、声紋
モデルそのものを疑った。いまは ReDimNet **b2**（`_voice_profiles.py` に直書き）
で、同じ配布元に b3/b5/b6 がある。

**この比較が再校正なしでできる理由**: 席の割当ては類似度のしきい値を使わない
（席を持つ人の中で1位を選ぶだけ）。上流の声紋層は b2 で校正済みなので記録の
まま固定し、席の割当てが使う埋め込みだけを差し替えた（`eval/embedding_model_compare.py`）。

| model | 全体 正解 | 誤帰属 | 開発5本 | 検証4本 | 埋込1回 |
|---|---|---|---|---|---|
| **b2（現行）** | 79.2% | 13.6% | 77.1% | 82.0% | **271ms** |
| b3 | 79.9% | 13.0% | 76.6% | 83.9% | 732ms |

**採らない。** 全体 +0.7pt に対し**開発セットではむしろ下がっており**（77.1→76.6）、

ライブでは採れない見込み。

この結果は §27.10（1635 で正解席の参照は純度100%なのに別人に寄る）や §27.14
（参照の作り方を変えても改善しない）と整合する。残る誤りは「モデルが小さい」
のではなく、**その録音でその話者対が実際に似ている**とみるのが自然。

なお b2 の値がこの独立したハーネスで 79.2%（開発77.1/検証82.0）と本番の測定に
一致したことは、`_recv_loop` の判定順序を正しく写せていることの確認にもなる。

## 28. 誤りは序盤に偏る——遡及訂正という未着手の大きな手（2026-07-26）

### 28.1 誤りの解剖（`eval/error_anatomy.py`）

「もう伸びしろは無いのか」を確かめるため、これまで切っていなかった断面で
残る誤りを分けた。**経過時間で切ったところで答えが出た**:

| 経過時間 | 発話 | 正解 | 誤帰属 | 未確定 |
|---|---:|---:|---:|---:|
| 0-1分 | 107 | **29%** | 16% | 55% |
| 1-2分 | 109 | 69% | 17% | 14% |
| 2-5分 | 379 | 77% | 22% | 1% |
| 5-10分 | 607 | **90%** | 9% | 1% |

**10分後には90%出ている。システムは収束していて、悪いのは立ち上がりだけ。**
にもかかわらず、いまは一度決めた帰属を**二度と見直していない**。

他の断面も併記する（いずれも「序盤」ほどの偏りは無い）:

- 発話長: 0.5秒未満は正解59%/誤帰属31%（201件）、4秒以上は95%/2%
- GT話者: S1 70% / S2 81% / S3 84%（S1 が弱い。§27.10 の1635と整合）
- またぎ: またぎ**あり**が84%、なしが76%。§27.13 の「区切りは主因でない」を
  再確認（またぎ発話は長いぶん当たりやすい）

### 28.2 遡及訂正の効果（`eval/retro_reattribution.py`）

席の参照が育った時点で、それまでの発話を**決め直す**とどうなるか。対象は
「席の音声で決めた発話」と「未確定のまま残った発話」だけで、声紋層が高信頼で
決めた発話（声紋一致・補正・自動登録・合流）は触らない。

| 条件 | 正解 | 誤帰属 | 未確定 |
|---|---|---|---|
| now（いまの実装） | 79.2% | 13.6% | 7.1% |
| 2分時点で貼り直す | 84.5% | 13.9% | 1.6% |
| **5分時点で貼り直す** | **89.5%** | **9.9%** | 0.6% |
| 終了時に一括（上限） | 93.1% | 6.9% | 0.0% |

開発5本 86.3% / 検証4本 **93.6%**（5分時点）。**目標の85%を大きく超える。**

### 28.3 なぜ実装できるのか

- **持つものが小さい**: 発話ごとの埋め込みは192次元。1200発話でも 1.8MB。
  音声を保持する必要はない
- **書き換え機構は既にある**: `SessionState.rekey` が過去レコード・色・台帳を
  一括で移す単一入口として存在する（今回は「特定の発話だけ」を移すので
  もう少し細かい入口が要る）
- **判定は既存のものをそのまま使う**: 席の音声との比較（`SeatAudio.nearest`）
  を、新しい参照で呼び直すだけ

### 28.4 決めるべきこと（未着手・要承認）

1. **いつ貼り直すか**: 5分時点が費用対効果の頂点だが、2分・5分・終了時の
   複数回でもよい（階段状に良くなる）
2. **表示の扱い**: 既に読まれた行の話者名が変わる。議事録としては最終成果物が
   正しいほうが良いが、会議中に目の前で変わるのは驚きになりうる
3. **手動修正の保護**: ユーザーが `/rename` や修正を入れた発話は上書きしない
   （`rekey` 経由の実名は保護対象）
4. **AI発話・相槌は対象外**（従来どおり）

### 28.5 実装と、予定表の校正（2026-07-26、正解89.9%）

ユーザー判断: 複数回やる／表示は「再判定しました」と出したうえで即座に
書き換える／ユーザーが付けた名前は上書きしない／終了時の一括は価値が薄い
（この製品はライブでの介入が目的で、終了後に直しても介入には効かない）。

**実装**:

- `_seat_audio.SeatAudio` を `embed` と `nearest_from` に分けた。声紋を1回
  計算して判定にも控えにも使い回すため（`nearest` は両者の薄い合成に変更）
- `_seat_audio.RetroAttributor`: 貼り直せる発話の声紋（192次元）を控え、
  予定時刻に達したら `nearest_from` を今の参照で呼び直す
- `SessionState.apply_retro_attribution`: records を書き換える。**対象は
  `speaker_source == "seat_assign"` か未確定だけ**——声紋層が高信頼で決めた
  発話は触らない（§27.12 の判断を変えない）
- `RecvLoop._maybe_retro_reattribute`: 時刻が来たら実行し、変わった件数を
  システム行としてタイムラインに残す（黙って書き換えない）
- `write_turns` は records から全文を書き直すので、保存物にも自動で伝わる

**予定表の校正**（`eval/retro_schedule.py`。本番クラスをそのまま駆動）:

| 予定表 | 正解 | 誤帰属 | 未確定 | 10分での回数 |
|---|---|---|---|---|
| 2分5分/**5分**ごと（初回実装） | 85.2% | 11.7% | 3.2% | 4 |
| 2分5分/**2分**ごと | **89.9%** | **7.0%** | 3.2% | 7 |
| 2分5分/1分ごと | 89.9% | 7.0% | 3.2% | 12 |
| 発話ごと | 89.9% | 7.0% | 3.2% | 毎発話 |

初回実装（5分ごと）が 85.2% に留まったのは、10分の会話だと 300→600秒に
一度も貼り直しが入らない区間ができるため。**2分でプラトーに達し、それ以上
細かくしても上がらない**ので、プラトーの入口である2分を採る。

貼り直しは保存済みの声紋と席の参照の内積だけで、**埋め込みの計算をしない**。
1200発話×3席でも内積3600回。間隔を詰めない理由は計算量ではなく表示の
書き換え頻度だけ、というのがこの表の意味。

**到達点**: 正解 **89.9%**（開発5本 89.5% / 検証4本 90.3%）、誤帰属 7.0%、
未確定 3.2%。この日の開始時点は 54.4% だった。

### 28.6 「参加者1人なのに参加者Bから始まる」の修正（2026-07-26）

実会話（screenrec_audio.wav）で確認された表示の不具合。**今日の変更の
副作用**である。

原因: 表示ラベル（参加者A/B/…）は「未使用の最小文字」をキーに割り当てる。
ところが席の割当て（§27.8）や遡及訂正（§28.5）で発話が別のキーへ移ると、
**元のキーは1件も発話を持たないまま文字だけ押さえ続ける**。参加者が
1人しか居なくても、先に文字Aを取ったキーが幻として残れば表示はBから
始まる。

修正 `SessionState.compact_anonymous_labels`: records に1件も現れないキーを
台帳から落とし、残ったキーへ**初出順**に振り直す。初出順を保つので、既に
見えている人同士の文字が入れ替わることはない（空いた文字へ詰まるだけ）。
実名で表示されているキーは `rekey` の時点で台帳から抜けているので触らない。

呼ぶ場所は遡及訂正の直後。表示が変わるのはもともと「再判定しました」と
告知している瞬間だけになり、黙って名前が変わることがない。遡及訂正が
走らない構成（pyannote単独・Soniox単独）では従来どおり詰め直しも起きない。

### 28.7 上限3なのに参加者Dが出る（席の横取り。2026-07-26 実会話で発覚）

`--max-speakers 3` で流したのに参加者A〜Dの4人が表示された。

**原因**: 自動登録（新しい人物Nの鋳造）の通知が `disp_name` で表示名を作って
いた。`disp_name` は未割当ての匿名キーに**ラベル文字を割り当てる副作用**を
持つ。しかもこの通知は `constrain_human_speaker_key` より**前**に走っていた。
constrain の規則は「既にラベルを持つ人は常に通す」なので、席が満杯でも
鋳造の瞬間に文字を確保したキーが、以後ずっと席持ちとして居座る。

同じ穴が「補正」の説明文（`disp_name(d['prev'])`）にもあった。

**修正**:

- 補正の説明文は `peek_disp_name`（割当てなし）に変更
- 自動登録の通知は **constrain の後**に移し、席を得られた場合だけ出す。
  落ちた場合は席が無いという警告（`_note_constrain_drop`）が別に出る

この「表示のために文字を先食いすると幻キーが席を食う」事故は、
`peek_disp_name` の docstring が 2026-07-14 の事例として既に警告していた
ものと同型である。partial 表示の経路は直っていたが、**通知の経路が残って
いた**。テストで固定した（修正前は 参加者D が出ることを確認済み）。

### 28.8 初回の貼り直しを60秒に（表示の都合。2026-07-26）

「最初の2分は参加者Bのままで、途中でAに変わるのが UX として悪い」という
指摘への対応。表示ラベルの詰め直し（§28.6）は貼り直しに同伴するので、
初回が2分だとそれまで醜い表示が続く。

§28.5 の予定表の測定で「1分ごと」も 89.9% とプラトー内にあることが確認
できているため、**精度を落とさずに窓を半分にできる**。予定表を
`(60, 120, 300)` + 以後120秒ごとに変更した。

なお根治は §28.7（席の横取り）の方で、そもそも幻のキーが席と文字を取らな
ければ B から始まらない。60秒化はその上での保険。

### 28.9 過去の登録者が席を素通りする（実会話で8人表示。2026-07-26）

`--max-speakers 3` で流した実会話の diag に、最終キーが8種類あった:

```
@diar:1, @diar:2, 人物1, 人物2, 人物3, ベテランち, 壁, 朱色
```

「ベテランち」「壁」「朱色」は**声紋層が返した実名**（kind=声紋一致 / 補正）
で、`voices.json` に入っていた。同ファイルには過去の会議から24人分が
蓄積されており、そこには名前の登録時に聞き間違えたと思われるもの
（壁・かべ・朱色・ペンタて・アリサか先生／ありさか先生の重複）が混ざる。

**原因**: `constrain_human_speaker_key` の先頭に

```python
if not (is_provisional_key(key) or looks_like_system_name(key)):
    return key   # 実名リネーム済みの人物は既存の席保持者
```

があり、実名キーは**上限の判定をまったく通らなかった**。会議中にリネームした
人を守るための例外だったが、`voices.json` がセッションをまたいで残るため、
「今回まだ一度も喋っていない過去の登録者」まで素通りしてしまう。

**修正**: 実名キーも席を要求する。「今回のセッションで既に席に着いているか」
＝ `_known_human_slots()`（表示ラベル or records に現れた実名キー）に含まれる
かで判定する。会議中のリネームは rekey で records ごと移るため席を保ち続け、
過去の登録者は席が空いていなければ未確定に落ちる。

`_known_human_slot_count()` は集合を返す `_known_human_slots()` に置き換えた
（数えるだけでなく所属も見るため）。

**残る課題（コードではなく運用）**: `voices.json` に溜まった24人は、UI から
削除する手段が無い（`/activate` で無効化はできる）。聞き間違いで作られた
プロファイルが増え続けるので、(1) 登録名の確認ステップ、(2) プロファイルの
削除手段、のどちらかが要る。当面は `voices.json` を消せばリセットできる。

### 28.10 遡及訂正が記録に残っていなかった（観測の穴。2026-07-26）

§28.5 で入れた遡及訂正は **records を書き換える**が、diag には何も書いて
いなかった。diag の発話ごとの行が持つ `final_key` は **flush 時点の値**で
あり、あとから貼り直しても更新されない（diag は追記専用）。

結果として、**記録から最終状態を復元できなくなっていた**。オフライン採点
（`eval/decompose_attribution.py` 系）はすべて diag の `final_key` を読むので、
今後のライブランを測ると遡及訂正のぶん（実測で約10pt）低く出る。今日の
測定はすべて 2026-07-20 の旧記録に対する再現なので影響していないが、
**次に録るランから効く**穴だった。

修正: 貼り直しのたびに diag へ1行残す。

```json
{"ms": ..., "type": "retro_reattribution", "changed": 12,
 "pairs": [[1000, "人物2"], ...]}
```

`apply_retro_attribution` は件数ではなく `{ms: 新しいキー}` を返すように変更
（diag に内容ごと残すため）。`decompose_attribution.load_run` はこのイベントを
適用してから採点する。追記専用という diag の性質は保ったまま、最終状態が
復元できる。

**教訓**: 表示（records）だけを直して記録（diag）を直さないと、後から
「本当はどうだったのか」が分からなくなる。今日は §26.6 でも同じ理由で
`speaker_source` を diag に足している。**状態を書き換える機能を足したら、
記録側にも同じ変更を残す**。

### 28.11 個別の穴ではなく「席の不変条件」を固定する（2026-07-26）

### 28.13 未確定18%の主因は「席で判定できなかった短い発話」（2026-07-27）

実会話（13.6分・340発話）の内訳。上限は守られていた（人物1/2/3 の3人）。
§28.12 の4人目は再現せず、`seat_admitted` の記録で理由も分かった——
`@diar:1`/`@diar:2` は constrain を通ったが**records には残らなかった**
（下流の席の割当てで別のキーに上書きされた）ので、席を占めていなかった。
数え方としては正しい。

残る問題は未確定18%（遡及訂正の反映後）。時間帯で見ると **序盤ではなく
後半に偏る**（0-1分12% / 1-2分23% / 2-5分9% / 5分以降20%）。Chiba とは
逆で、遡及訂正では取れない。

内訳を追うと原因がはっきりした。席の音声で判定すべき「ラベル不純／ラベル
継続」178件のうち、**53件が判定できずに未確定のまま**残っていた。
判定できた分と比べると明確に短い:

```
判定できた 125件: 秒数 中央値 0.66  / 0.5秒未満 41件
できなかった 53件: 秒数 中央値 0.30  / 0.5秒未満 40件
```

ただし**合成音声では0.06秒でも埋め込みは計算できる**（ReDimNet b2 で確認）。
つまり「短いから声紋が作れない」とは限らず、実際の音声スライスが無音・
空だった可能性がある。ここも推測で潰さず、判定できなかった理由
（`no_embedding` か `few_seats:N` か）を diag に `seat_miss` として残す
診断を足した（挙動不変）。

なお遡及訂正が期待より効かない（4回で計8件）のも同じ原因である。
`remember` は席の判定を試みた発話の声紋を控えるが、声紋が None なら何も
控えられないため、後から決め直す材料が無い。

### 28.14 訂正: 未確定18%は数え方の誤り。実質は6%（2026-07-27）

`seat_miss` の診断を入れて実会話を再測した結果、**§28.13 の見立ては誤り**
だった。順に訂正する。

**(1) 席で判定できなかったのは53件ではなく10件**。しかもその10件は全て
「まだ席が2つ育っていない」序盤のもので（`few_seats:0/1`）、**最終的に
未確定として残ったものは0件**だった。声紋が計算できなかった例
（`no_embedding`）は1件も無い。§28.13 で「53件が判定できず」としたのは、
`seat` フィールドが無い発話を数えたためで、その大半は**相槌**だった——
相槌は席の判定を通らない（設計上つねに未確定。§13.2）。

**(2) 未確定18-20%は分母の取り方が違っていた**。この日の Chiba の測定は
すべて「相槌を除く実質発話」を分母にしていたのに、実会話の集計だけ相槌を
含めていた。揃えると:

```
未確定 61件 / うち相槌 44件
実質発話 279件 中 実質未確定 17件 = 6%
```

Chiba の 3.2% と比べられる数字はこちら。**6%** である。

**(3) 残る17件の主因は重なり**。11件が `multiple_diarization_speakers_overlap`
または `diarization_overlap_*`＝複数人が同時に話している区間で、声紋が
あてにならないため安全側で未確定にしている。残りはラベル不純3件など。
つまり**取れる余地はほとんど無い**。

**席の上限も守られていた**（人物1/2/3の3人）。`seat_admitted` の記録では
`@diar:1`/`@diar:2` も席を通っているが、下流の割当てで上書きされ records に
残らないため席を占めていない。

**教訓**: 実会話の集計と Chiba の集計で分母が違うまま比較していた。
以後、実会話の未確定率は必ず「相槌を除く実質発話」で出すこと。

### 28.15 登録した声を UI から削除できるようにする（2026-07-27）

## 30. 実ドメインを測ろうとして、測定の土台が壊れていた（2026-07-28）

89.9% は千葉（クリーン音源）9本の数字であり、実会話で出るかは未確認のまま
だった。手元に**実会議マイク録音のGT**（`2026-07-14_142016`、82発話・3人・
4分）があったので、これで測ることから始めた。

### 30.1 出た数字と、その裏にあったもの

今日の実装で採点すると **正解 55.1% / 誤帰属 24.6% / 未確定 20.3%**
（旧形式で `final_key` が無いため `key` で代用。相槌は除外）。千葉の 89.9%
とは 35pt の開きがある。

原因を「ドメインが難しいから」で片付けず、埋め込み自体の分離上限を測った
（正解ラベルで作った参照への leave-one-out 最近傍＝オラクル）:

| run | n | オラクル上限 | 同話者sim | 別話者sim | 差 |
|---|---:|---:|---:|---:|---:|
| 2026-07-14_142016（実会議マイク） | 69 | **42.0%** | 0.142 | 0.124 | 0.018 |
| 2026-07-20_1623（千葉） | 103 | 97.1% | 0.456 | 0.183 | 0.273 |
| 2026-07-20_1635 | 125 | 89.6% | 0.297 | 0.164 | 0.133 |
| 2026-07-20_1655 | 168 | 97.0% | 0.404 | 0.098 | 0.306 |

3人の録音でオラクル 42% は偶然（33%）とほとんど変わらない。ところが**長い
発話だけ**を取り出すと、142016 でも同一話者 0.77–0.79 / 別話者 ≈0.00 と
綺麗に分離する。壊れているのは短い発話だけだった:

| 発話長 | 142016 | 千葉1623 |
|---|---:|---:|
| 0-1秒 | **7%** | 50% |
| 1-2秒 | **5%** | 76% |
| 2-3秒 | **0%** | 100% |
| 3-5秒 | 62% | 100% |
| 5秒以上 | 100% | 100% |

**偶然を下回るのは、当たっていないのではなく系統的に外れている**ということ。
窓が隣の話者の音声にかかっている疑いが濃い。

### 30.2 原因: 録音wavと発話msが別の時計だった

オフセットを掃引すると山ができた。千葉は +0ms が最良（83.5%）、142016 は
**+2250ms で 24.6% → 55.1%**。しかも前半 +1500ms・後半 +2500ms と、ずれが
時間とともに増える。エネルギーだけの照合（話者性を使わない）でも、千葉は
0ms、142016 は一貫して正のずれを示した。

コードに原因があった。`_workers.py` の音声送出ループは

- 録音wav（`pcm_file`）には**取り込んだ全チャンク**を書く
- ASR用バッファ（`asr_pcm_buf`）には**STTへ送信できたチャンクだけ**を足す

発話の ms は送信済みバイト位置そのもの（`asr_pcm_total_bytes // 32`）なので、
ws 再接続中や送信例外で送れなかった分だけ**wav が先へずれ、二度と戻らない**。
千葉はファイル供給で送信が安定していたためずれず、実マイク収録だけがずれた。

**ライブの帰属は影響を受けない**（本番は wav ではなく `asr_pcm_buf` を ms で
切っており byte 単位で一致）。壊れていたのは、記録を後から測る側と、
音声を聴いて正解を付ける側である。旧アノテーターに「ズレ補正」という手動の
つまみが付いていたのは、この症状を人手で吸収していたということでもある。

**修正**（`c3616cb`）: wav への書き込みを送信成功後に移し、ヘッダ長も
`asr_pcm_total_bytes` に合わせた。送れずに録音へ入らなかった秒数は
`finalize_wav` が知らせる。回帰テストは「送信に失敗したチャンクが録音に
混ざらないこと」と「wav 末尾の ms が次の発話の原点と一致すること」を見る。

### 30.3 この件から引く教訓

- **ドメイン差を語る前に、その音源で埋め込みが分離できるかを測る。**
  オラクル上限は正解ラベルさえあれば数分で出る。上限が低ければ、
  ロジックをどういじっても伸びない。
- **偶然を下回る数字は「難しい」ではなく「ずれている」の合図。**
  33%を狙う3択で0-7%が出たら、まず対応関係を疑う。
- 千葉が 89.9% でも実会話が同じとは限らない、という当初の懸念は残る。
  今回の 55.1% は**測定が壊れた状態での下限**であって、実力値ではない。
  実ドメインの数字は修正後の録音で取り直す（142016 のGTは参考値に降格）。

### 30.4 注釈ツールの作り直し（`596385f`）

10分ぶんの正解を付ける作業を、段取りではなく耳と指だけの作業にする。

- ローカルサーバとして立ち、音声を Range 付きで配る（ファイル選択が不要）
- 押すたびに `eval/gt_<名前>.json` へ自動保存（既存項目は保持、初回のみ
  `.bak`、一時ファイル経由で差し替え）。閉じても続きから再開できる
- 話者は9人まで。`1`〜`9` で話者、`S` で直前と同じ、`0` 不明、`M` 複数人
- 「自動送り」は1区間鳴らして止まり、キーを押すと次へ進んで自動で鳴る
- 収録セッション以外の任意の音声も扱える（文字起こしが無ければ無音で区切る）
- 全体波形にラベル済み区間を色で表示

採点側の `GT_CODES` も9人に広げた（`e7b278c`）。3人の録音の数字は不変
（9本平均 89.9%/7.0%/3.2% を再確認）。

## 31. バグの徹底監査と _workers.py の分割（2026-07-28）

### 31.1 確認できたバグ（4件、いずれも1件1コミット）

**(a) 表示ラベルの割当てが競合する**（`7708e21`）。`_anonymous_label_for` は
「使われていない最小の文字」を選ぶため、使用中の集合を読んでから辞書に書く
までに間がある。`disp_name` は受信スレッド（発話確定）からも UI スレッド
（描画・API）からも呼ばれるので、その間に別のキーが同じ文字を取れる。

重複は表示の紛らわしさに留まらない。**人数上限の判定 `_known_human_slots` は
表示ラベルの集合で席を数える**ので、2人が1席に潰れ、上限を超えて席が空いて
いるように見える（`--max-speakers 3` なのに4人目が座る）。`state_lock` を
RLock にして割当てを守った（`write_md`/`write_html`/`write_turns` は
ロックを持ったまま `disp_name` を呼ぶため、素の Lock では自分を待って止まる）。

**(b) 合流で席の参照が短いほうに上書きされる**（`0c6e591`）。
`SeatAudio.rename` は `store[new] = store.pop(old)` で素直に移していた。
付け替えは改名だけでなく「分裂したクラスタを1人に束ねる」合流でも呼ばれる
ため、統合先が貯めた30秒の参照が統合元の数秒の参照で消えることがあった。
さらに凍結の印は old 側からしか伝わらないので、**短い参照のまま凍結され
二度と育たない**。長いほうを残すようにした。9本の数字は不変（記録の再生は
リネームを含まないため、この修正はライブでのみ効く）。

**(c) diag に前の発話の判定が書かれる**（`7014a93`）。STT が話者ラベルを
返さない発話では classify を呼ばず `d=None` にしているのに、diag は
`tracker.last`（前の発話の残骸）を書いていた。手元の記録では該当0件だが、
採点も分析も diag の `kind` を信じて動くので、ずれると静かに全部が狂う。

**(d) 声紋によるAIエコー除去が記録に残らない**（`f93427f`）。テキスト安全網
（agent/partner/retired）は `echo_drop` を1行書くのに、声紋経路だけ黙って
捨てていた。3経路の書き出しを `_note_echo_drop` にまとめて揃えた。

### 31.2 却下した指摘（調べた結果、バグではなかった）

- **候補が1人のときマージンが効かない**: 2位が無いのだから設計どおり。絶対
  しきい値 `sim >= need_th` は効いている
- **遡及訂正が `diarization_speaker_keys` を更新しない**: 発話単位の訂正で
  あって同一性の付け替えではない（docstring に明記済み）
- **`_key_of` のロック漏れ**: `rekey` 側が `list()` でコピーしてから回すので
  イテレーション中の変更にならない
- **区間の逆転**: `stt_time_offset_ms` は単調増加なので `end < ms` にならない

**この監査から引く教訓**: 最初 (a) を「`RuntimeError` でセッションが落ちる」
と報告したが、再現しなかった。`set(dict.values())` は C の中で完走するので
他スレッドに割り込まれない。**機構を口で説明できても、再現するまでは
バグと呼ばない**。再現テストを書いたら、本当の実害（ラベル重複→席の
数え落とし）はそこにあった。
