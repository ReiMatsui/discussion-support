# 自分で実行する、使用量を制限したLLM接続確認

## 目的

AI側では課金のない人工入力検査を行い、実APIを使う確認は本人が明示して実行する。最初は人工会話1件の接続・出力確認にとどめる。旧 `das.study.probe` もこの機能を呼ぶ入口に統合し、既定では送信しない。音声API・録音・実験参加者のデータは使用しない。

OpenAI Docsスキルで[公式のChat Completions仕様](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create)を確認し、出力上限と応答に含まれるusageを利用した。新しいモデルへの変更はしていない。

## 上限

- 通常起動は送信しない。実行計画のみ表示する。
- `--execute`を付けた1回の実行につき、HTTPリクエストは最大1回。
- 同じ利用記録を使う限り、累計3回まで。日付や再起動ではリセットしない。同時実行も記録のロックにより合算する。
- 1回の出力は最大6,000トークン。推論モデルでは推論分も含む。`--max-output-tokens`で減らせるが、6,000より増やせない。小さすぎる上限ではJSONが完成しないことがある。
- 入力は、指示・会話・出力形式等を含む送信JSON全体で32KiB以内。これは入力トークン数の厳密な上限ではない。
- 400・401・429・通信切断・タイムアウト・不完全なJSONでも、自動再試行しない。リダイレクトにも従わない。
- 失敗や途中終了も1回分として予約する。タイムアウト等では、サービス側で処理・課金されたか分からないためである。
- 使用量が応答に含まれれば、解析失敗・出力上限による終了でも結果ファイルと累計記録に保存する。結果ファイルを上書きしない。
- 既存の `das.llm.cost.CostTracker` を使用して、実測の入力・出力トークン数と推定費用を集計する。再起動後は同じ利用記録から再集計する。
- 既定の費用予算は累計 **0.10 USD**。次の1回の予約額を加えて予算を超える場合は、送信前に止める。`--budget-usd`で初回の予算を指定できる。新形式の予約を保存した後は、同じ利用記録の予算を途中で変更できない。
- 未取得の使用量は0扱いにせず、送信JSONのUTF-8バイト数＋1,024と出力上限を使って費用を見積もり、予約額を保持する。使用量が返った分だけ実測値で置き換える。この見積もりは正確な入力トークン数ではない。
- 未登録モデルの安い既定単価へフォールバックして予算を通過させず、費用の予約を拒否する。

**予算制御は見積もりに基づき、請求額の厳密な上限を保証するものではない。** 費用はモデル単価と実際の入力・出力等で変わる。キャッシュ割引等を反映した請求書の金額ではない。gpt-5.4-miniの料金表の入力・出力単価は2026年11月5日に[公式モデルページ](https://developers.openai.com/api/docs/models/gpt-5.4-mini)と一致することを確認した。3回という制限はこのスクリプトのみを対象とし、通常の実験システムや他のスクリプトには適用されない。初回は1回だけ実行し、結果と使用量を確認してから次へ進む。

## 実行

ターミナルでリポジトリへ移動する。

```sh
cd /Users/matsuirei/discussion-support
```

まず送信せず、設定を確認する。

```sh
.venv/bin/python -m das.study.bounded_probe
```

モデル、送信サイズ、出力上限、自動再試行0回、使用済み回数、実測使用量の集計、不明分の予約額などが表示される。この操作ではAPIキーの有効性までは確認しない。

ローカルの `.env` の `OPENAI_API_KEY` を確認した上で、1回だけ実行する。

```sh
.venv/bin/python -m das.study.bounded_probe --execute --out study/probes/user_check_01.json
```

キーをチャットへ貼る必要はない。既に環境変数が設定されていれば、従来どおり `.env` より優先される。

2回目を実行する場合は、出力名を `user_check_02.json` などに変える。すぐに連続実行せず、前の結果を確認する。401の場合は認証設定を直すまで再実行しない。

## 見るところ

- `status`：`completed`なら接続・JSON検査・根拠検査が通過した。介入が有効だったという意味ではない。
- `http_status`：401などのHTTPエラー。エラー本文やキーは保存しない。
- `usage`：その1回の実際の入力・出力トークン数等。応答が得られなかった場合は記録できない。
- `cumulative_usage.reported_usage`：既存CostTrackerで集計した、応答に使用量が含まれた試行だけのトークン数・推定費用。
- `cumulative_usage.unknown_usage_attempts` / `held_estimate_usd`：使用量が分からない試行数とその予約額。実測費用が0と表示されても、不明分が無料だったことを意味しない。旧形式の1回目の失敗記録もここに含む。
- `message` / `failed_phase`：認証失敗や予算による停止などの理由。HTTP 401も端末へ表示する。
- `finish_reason`：`length`なら出力枠で打ち切られた。自動では追加生成しない。
- `decision` / `prepared_text`：引用に基づく候補を生成できたか。

利用回数の記録は `study/probes/bounded_usage.jsonl`。この記録を削除したり、別の作業フォルダから実行したりすると累計の制限を引き継げないため、上記の同じフォルダで使う。上限を使い切ったら、結果を確認して次の検証規模と予算を決める。自動リセットは実装していない。

## 今回行ったテスト

実APIは呼ばず、送信しない既定動作、出力・入力の上限、4回目の拒否、同時実行の合算、失敗時の1回消費と自動再送なし、結果の上書き拒否、使用量の保存、成功時の根拠検査を模擬通信で検査した。

通常システムと同じ抽出指示・出力形式・根拠検査を使う。ただし、この確認用では再試行を避けるため推論の設定を明示的にlowにしている。実運用と完全に同じ遅延や精度を再現する検査ではない。

## 整理の方針

実行時と接続確認の抽出指示・会話の組立て・出力形式は `build_review_params` に共通化した。費用集計は既存CostTrackerを再利用し、料金計算を複製しない。通信自体は自動再試行のある既存クライアントに切り替えず、この検査に限って1回だけの送信を維持している。CostTracker自体の料金表や既存の予算仕様は変更していない。

今回の整理でも実APIへの送信はしていない。前回本人が実行した1回・残り2回の記録を維持した。
