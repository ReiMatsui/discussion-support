# ライブ介入のレイテンシ実現可能性検証

最終更新: 2026-06-12（Claude / Cowork セッションでの実測）

## 方法

本物の `Orchestrator` + `EventBus`（コード無改変）に、現実的な遅延を再現するフェイクLLMを
注入し、**実会議の発話ペース**（speaker-attribution の実セッション 2026-06-11_1157、
発話間隔の実測列）でリプレイ。時間スケール圧縮（ペースとLLM遅延を同率で1/8、結果を逆スケール）。
再現ハーネス: /tmp/das_latency.py 相当（要 Python3.11 + das core）。

## 結果

| LLM遅延プロファイル | 発話→グラフ反映 p50 | p95 | 同時実行タスク 平均/最大 | 終了後の残処理 |
|---|---|---|---|---|
| 軽量（nano級: 抽出0.8s/判定0.6s） | 0.9s | 1.0s | 0.7 / 4 | 1.6s |
| 中量（mini級: 抽出1.5s/判定1.0s） | 1.7s | 2.0s | 1.2 / 4 | 3.2s |
| 重量（4o級: 抽出3.0s/判定2.0s） | 3.1s | 3.9s | 2.2 / 6 | 5.2s |

**重要な観察: どのプロファイルでも処理の滞留（backlog暴走）は発生しない。**
EventBus が発話ごとに `create_task` する設計のため、会話ペース（平均3〜4秒/発話、
応酬時1秒台）に対してパイプラインが線形に追従する。アーキテクチャは既にライブ向き。

## エンドツーエンドの介入レイテンシ予算

```
発話終了 → STT確定(Soniox) ≈1-2s → 声紋話者特定 ≈0.03s
        → 抽出+リンク(上表) 1-4s → 介入判定 → 提示
合計: 約3〜7秒（中量モデル時）
```

presentation_policy.md の設計と突き合わせると:
- **in-flow（個人宛1行通知）**: 関連発話から3〜7秒後の到達。会話の文脈が生きている
  窓（〜10秒）に収まる → **成立**
- **breakpoint（区切りでの全員向け一文）**: 分オーダーの余裕 → 問題なし
- 介入の検出条件はAFから決定的に計算（LLM judge非依存）と設計済みのため、
  facilitation自体の追加遅延はほぼゼロにできる

## 結論と次の作業

**実現可能。ボトルネックは計算でも遅延でもなく、配線の不在。**

1. **FacilitationAgent が run_live に未配線**（現状 eval/conditions.py のみで使用）。
   NodeAdded/EdgeAdded 購読 or 数発話ごとの判定でバスに接続するのが次の実装。
   l2_min_interval 等のゲートは実装済みで流用可。
2. 相槌・短発話（<数文字）を Extraction に送らないフィルタを入れると、
   コストとノイズが大きく減る（実会議ログでは発話の3〜4割が相槌）。
3. モデルは抽出・判定とも軽量級で十分（linking_model override は実装済み）。
   重量級でも遅延は約2倍になるだけで破綻はしない。
4. 提示の出口は最初は das の標準出力（既存方針通り）で検証可能。
