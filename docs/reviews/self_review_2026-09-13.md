# セルフレビュー（2026-09-13）: 実会議で起こりそうな問題

GPT-Live 移行（WP1〜8）のあと、実マイク試行（WP9）の前に、システム全体を
「ノート PC 1 台・内蔵マイクとスピーカー・2〜3 人・10 分」の前提で読み直した。
観点は 3 つ: 介入のタイミングと中身、話者同定と議事録、止まらないこと・復旧。
コードを追って裏が取れたものだけを載せる。修正したものはコミット
`fix(live): セルフレビュー（実マイク・内蔵スピーカー前提）で見つかった欠陥の修正`
に入っている。ここには「直したこと」の要約と、設計判断が要るので直していない
ものを残す。

## 1. 直したこと（要約）

### 止まらないこと・復旧

| 症状 | 原因 | 直し方 |
|---|---|---|
| Ctrl+C が効かず kill するしかない（wav のヘッダが壊れる） | 受信ループが KeyboardInterrupt を握りつぶし、呼び出し側が run() を再入 | 停止要求として扱う |
| GPT-Live が接続済み表示のまま永久に黙る | イベント処理の例外で受信スレッドが死に、_connected が True のまま | 1 イベントの失敗で死なせない |
| 介入も再接続も静かに止まる | 介入ワーカー（1 本で発火と再接続を兼ねる）が例外 1 回で終了 | 理由を出して再入 |
| 相手役が切れたまま | 誰も張り直さない | ワーカーが 5 秒間隔で再接続 |
| AI が永久に黙り「話し中」も戻らない | 再生スレッド（sounddevice）が死ぬと終端マーカーを誰も取らない | 監視で立て直す |
| Wi-Fi が詰まるとマイク入力そのものが欠ける | マイクのコールバック内で WebSocket 送信 | 送信待ちに積み、送信スレッドが送る。3 秒以上の溜まりは捨てる |
| 発話終端の二重処理 | _finish_turn が受信と監視の両スレッドから走る | 1 発話 1 回に |

### 話者同定・議事録

| 症状 | 原因 | 直し方 |
|---|---|---|
| 発話が直前の話者に誤帰属、同一人物が 2 席に分裂 | 既定の UI 起動では STT 接続→分離接続の約 1 秒の音声が分離に届かず、以後の区間が STT より早い側にずれる | 未接続中の音声もタイムラインに足す |
| 「新しい会議」の後、話者分離が事実上死ぬ | 分離の時刻が前会議の長さぶん先行 | 0 に戻す |
| 人が相手役の言葉を引用して反論すると発言が消える | 相手役のテキスト類似エコー除去に再生区間の門が無い | 区間で門を掛け、相手役の再生区間も記録 |
| 声を変えた直後、旧声のエコーが人の発言になる | 旧声紋を先に消していた | 上書きされるまで残す |
| AI 発話の末尾が議事録から欠ける | 文字が音声に遅れて届く | 文字が 0.3 秒止まるまで確定を待つ |
| AI 声紋の質が下がる | 無音チャンクも登録に使っていた | 有声チャンクだけ |

### 介入のタイミングと中身

| 症状 | 原因 | 直し方 |
|---|---|---|
| 呼びかけに二度答える | GPT-Live が直接答えたあと、STT→triage 経由の manual_call が同じ依頼を発火 | 直前に指示なし発話があれば「直接応答済み」として再送しない。アック音も鳴らさない |
| 沈黙介入で何を言うか不定（論点を読み上げる等） | 指示文が論点一覧だけ | [沈黙] の指示（一言で整理し、次を一つ提案） |
| 同じことを繰り返す | 「直近の発言を繰り返さない」注記が thinking 側に落ちていた | 指示側に |
| 15 秒待って諦めた指示を後で話し出す | 指示がモデルに残る | 取り消しを送る |
| 介入が長く出ないと何千字も一気に送る | 溜めた発話に上限が無い | 40 件で打ち切り、添えるのは直近 15 件 |
| 指示なし発話の回数が汚れる | 文の間で割れた続きを数えていた | 終端から 4 秒内の再開は続き |
| 介入ログが 0.25 秒ごとに 2 行 | レーンが交互に「変化あり」 | 候補集合ごとに前回を持つ |

## 2. 直していないこと（設計判断が要る）

優先度は実マイク試行への影響で付けた。

### 高: 実マイク試行の前に決めたい

（追記 2026-09-13 夜）A と B は決めて実装した。A は脱線を「議題外の話が続いた時間」で
測る状態機械に置き換え（`_drift.py`、閾値は積極性プロファイルの `drift_run_sec`:
standard 45 秒 / active 25 秒 / controlled 90 秒、確認回数のゲートは廃止）。
B は GPT-Live の直接応答を主とし、文字起こし経由は聞き逃しの保険として残す。
replay では指示なし発話を「呼びかけへの応答」と「それ以外」に分けて数える。
C は当面そのまま（試行は名前を登録して始める）。


**A. standard プロファイルでは脱線介入がほぼ出ない。**
脱線は 2 回連続の検出が要るが、検出は 3 発話ごと（20〜30 秒）で、確認の窓
（20 秒、`_intervention.py` の drain にハードコード）と候補の寿命（30 秒）を
たいてい超える。さらに論点抽出が脱線先の話題を論点として取り込むため、2 回目の
判定が「関連話題内」になる。直前のシミュレーションでもこの経路で消えた。
選択肢: (1) 確認の窓を寿命と揃えて 40 秒程度にし、cooldown 中は候補を捨てず保持する
（Controller の規則に触る）、(2) 論点抽出に「議題から離れた話題は論点にしない」を
入れる、(3) 試行では active（確認 1 回）で運用する。試行だけなら (3) で足りる。

**B. 呼びかけ応答の方針が二重に生きている。**
GPT-Live が直接答える（プロンプトで許可）経路と、STT→triage→manual_call の
経路の両方がある。今回の修正で二度話すことは止めたが、どちらを正とするかは
未決（計画 §9-2）。直接応答は速い（約 1 秒）が Controller を通らないので
記録は「指示なし発話」になる。試行で直接応答の回数と質を見てから決める。

**C. 匿名の参加者への声かけ。**
名前を登録していない会議では「参加者C さんはしばらく発言していません」と
言うが、室内の誰も自分が C だと分からない。声かけは実名登録済みの話者に限る
か、匿名なら「まだ発言の少ない方はいかがですか」に言い換える。試行では名前を
登録して始めるのが確実。

### 中: 試行の結果を見てから

- **事実補正の鮮度**: 候補の寿命 30 秒は長く、最悪 35 秒前の断定を訂正する。
  10〜12 秒に詰め、fact も global cooldown の対象にする案。
- **整理介入（summarize）に寿命が無い**: 保留中に判定が変わっても古い焦点が残る。
  30〜40 秒の寿命を付ける。また価値判定 LLM が 10 発話目以降は毎発話走る
  （10 分で 70〜100 回）。3 発話ごとに。
- **AI 行の並び順**: AI の行は ms を持たず確定時刻で並ぶので、STT の遅れが大きいと
  質問より前に答えが並ぶ。delivery の capture_start_ms を ms に入れれば並べ替え
  られるが、遡及訂正などの ms を使う処理への影響を確認してから。
- **人の発言が AI エコーとして消える方向の誤り**: AI 発話中に人が被せた短い発言が、
  声紋の類似 0.50 超で丸ごと捨てられうる。捨てずに「未確定・エコー疑い」で残す案。
- **マイク入力の死活監視が無い**: デバイス変更やスリープ復帰でコールバックが
  止まっても UI に何も出ない。最終コールバック時刻を見て警告と再オープン。
- **pyannote の再接続が送信スレッドを止める**: 再接続の HTTP+WS 接続（最悪 25 秒）が
  STT 送信も止める。60 秒に 4 回失敗すると以後は再試行しない。専用スレッド化と
  定期再試行。
- **UI に GPT-Live の接続状態が出ない**: /api/state には載せた（connected / ready /
  conn_error）。画面の表示はまだ。
- **名乗り登録に AI 区間の門が無い**: AI の声が混ざった音声で声紋を永続化しうる。

### 低

- 介入オフでも GPT-Live は室内を聞き続け、呼びかけには答えて議事録にも載る
  （意図ならよいが UI の文言と合わせる）。
- 進行役と相手役が同時に鳴る（converse モード）: 相手役は進行役の声をスピーカー
  経由で聞いて譲るが、同時に話し始めた場合は止まらない。内蔵スピーカーでは
  相手役が自分のエコーで自分を止めることもありうる。試行で `end_reason` と
  `unrequested_turns` を見る。
- 未確定（?）の発話は長さに関係なく介入の文脈から外れる（docstring は「短発話」）。
- `elapsed_ms` は壁時計、発話 ms は送信バイト基準なので、切断やスリープ後に
  システム行の時刻だけ先行する。
- 終了時の WebSocket close の待ち（既定 10 秒 × 2）でネット死亡時の終了が遅い。

## 3. 問題なしと確認した領域

pause 検出は partial 更新中を沈黙 0 とみなす保守側。エコー窓と floor 返却
（窓明けで last_utt_time をリセット）。Soniox 側の区間ベースのエコー除去は遅い
final にも効く。barge-in レーンも wait_for_pause で被せない。epoch による stale
決定の破棄。Soniox 再接続の ms 整合。pyannote の先行ガード。GPT-Live の世代番号
による開き直し。trigger の送信失敗時に候補を消費しない。save() の tmp+replace。
AI/相手役は席・発言量・声かけ対象から除外。遡及訂正は AI 行に触れない。

## 4. 実マイク試行で見るもの

介入ログ（`transcripts/<日時>.interventions.jsonl`）と `replay` の Live チップ:
指示→声の遅延の中央値と最大、指示なし発話の回数（呼びかけ応答か、それ以外か）、
人の発話との重なりと黙るまでの時間、自力で再開した回数。加えて `.log` の
「再接続」「立て直し」「取り消し」の行数。0 でなければその経路が実際に踏まれている。
